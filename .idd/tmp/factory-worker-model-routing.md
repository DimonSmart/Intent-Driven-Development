# План: запуск Factory worker на модели назначенного уровня

Дата: 2026-10-05. Статус: план реализации.

## Цель и принятые решения

Каждая задача получает от планировщика обязательный `ExecutionProfile`:
`economy`, `standard` или `strong`. Оркестратор создаёт worker с моделью и
параметрами reasoning, заданными для этого профиля в конфигурации проекта.
Worker не выбирает собственную модель.

- Старых планов нет: миграция и default `standard` для отсутствующего профиля не нужны.
- Профили обозначают сложность и остаются стабильными при смене моделей.
- Конкретные ID моделей и параметры reasoning хранятся в `.idd/execution.yaml`.
- В режиме маппинга обязательны все три соответствия для активной платформы.
  Неявного наследования для отсутствующего соответствия нет.
- Существующий явный `modelStrategy: inherit` сохраняется как отдельный выбор
  пользователя: использовать модель сессии для всех задач. В этом режиме
  различие профилей не означает различия моделей.
- Если конфигурации нет, настройка должна завершиться до запуска первого worker;
  отсутствие файла не считается разрешением на неявный `inherit`.
- Автоматической замены модели или изменения профиля при ошибке нет.
- Изменения остаются в архитектуре native-agent Factory: канонические инструкции,
  платформенные адаптеры, генератор, отчёт и тесты. Отдельный runtime не добавляется.

## 1. Обязательный профиль в контракте планировщика

Изменить `src/canonical/skills/idd-factory-decompose-task.md`:

- Требовать ровно один `# ExecutionProfile` для каждой `# Task`.
- Сохранить три канонических значения и критерии сложности.
- Удалить optional/default-поведение, включая примеры задач без профиля.
- Отсутствующий, неизвестный или повторный профиль считать некорректным планом;
  affected worker не запускать, сообщать конкретную ошибку.
- Сохранить разделение ответственности: планировщик не читает маппинг, не
  выдаёт модель и не учитывает стоимость либо доступность моделей.

Согласовать правила с `idd-factory-run.md` и
`src/canonical/methodology/factory-execution-policy.md`.

## 2. Полный и изменяемый маппинг

Обновить каноническую execution policy. Использовать текущую форму YAML:

```yaml
version: 1
factory:
  executionProfiles:
    economy:
      codex:
        model: <concrete-model-id>
        reasoningEffort: <supported-value>
    standard:
      codex:
        model: <concrete-model-id>
    strong:
      codex:
        model: <concrete-model-id>
        reasoningEffort: <supported-value>
```

Для Claude сохраняются `claude.model` и необязательный `claude.effort`.
Параметры reasoning необязательны; допустимые значения определяет платформа.
Одна модель может использоваться для нескольких профилей.

Валидация до запуска: `version: 1`, ровно одна стратегия, известные профили и
платформы, непустые ID моделей, корректная структура, полный маппинг для
активной платформы. Частичный маппинг больше не поддерживается. Отдельный
флаг строгого режима не нужен, поскольку совместимость со старой политикой
наследования не требуется.

## 3. Создание и обновление конфигурации

Обновить `src/canonical/skills/idd-factory-configure.md`:

1. Читать текущую политику, если она есть. При ошибке показывать диагностику;
   исправление выполнять в рамках настройки, без молчаливой замены стратегии.
2. Для создания или обновления маппинга получать сведения из нативного каталога
   моделей хоста, затем из информации платформы/актуальной официальной
   документации, либо из конкретных ID, предоставленных пользователем.
3. Предлагать полное соответствие всех трёх профилей. Не встраивать
   рекомендуемые ID моделей в исходники IDD и не утверждать доступность
   модели для аккаунта без подтверждающих данных.
4. При обновлении показывать таблицу: профиль, текущая модель/reasoning,
   предложенная модель/reasoning. Разрешить изменение отдельных строк при
   сохранении полного итогового маппинга.
5. Получать подтверждение конкретного предложения, валидировать и сохранять
   конфигурацию атомарно, когда файловые инструменты это позволяют.
6. Повторно читать сохранённый файл и сообщать итоговое соответствие.

Запросы «обнови модели» и «используй актуальные модели» разрешаются в конкретные
ID во время настройки. Динамические алиасы не сохраняются. Автоматического
фонового обновления нет. Интеграцию первоначальной настройки согласовать с
`idd-project-init.md` и preflight `idd-factory-run.md`.

## 4. Применение при каждом запуске worker

Обновить `idd-factory-run.md`, `CodexPlatformAdapter.cs` и
`ClaudePlatformAdapter.cs`:

```text
Task.ExecutionProfile
→ заново прочитать execution.yaml
→ проверить политику
→ получить точное соответствие для активной платформы
→ передать настройки в native child-agent spawn
```

- Для Codex явно описать преобразование `codex.model` в `model`,
  `codex.reasoningEffort` в `reasoning_effort`, с `fork_turns: "none"`.
- Для Claude описать применение модели/effort через доступные нативные
  параметры конкретного хоста. Неподдерживаемый явный override блокирует запуск.
- Для явного `inherit` не передавать model/reasoning overrides.
- Не переоценивать сложность и не подбирать другую модель после lookup.
- Не передавать worker инструкцию «переключи модель»: модель задаётся при
  создании агента. Skill worker остаётся `idd-factory-execute-subtask`.
- При отклонении настроек хостом сообщать профиль, запрошенные настройки и
  причину ошибки; предлагать повторную настройку без запуска замены.

Настройки одного запуска фиксируются из одного прочитанного документа.
Обновление файла после этого не меняет работающего worker. Следующий запуск,
включая задачу из уже составленного плана, читает новый маппинг. Перепланирование
для смены модели не требуется.

## 5. Отчёт о фактически применённых настройках

Расширить `tools/idd-factory-report/ReportTool.cs` и документацию отчёта:

- Связать профиль задачи с конкретным worker/thread.
- Показывать профиль, запрошенную модель и reasoning из аргументов spawn.
- Отдельно показывать фактическую модель/reasoning, если нативный trace
  предоставляет такие данные; иначе оставлять их неизвестными.
- Не выводить фактическую модель из текущего `execution.yaml` или настроек root.
- При доступных данных о расхождении запрошенных и фактических настроек
  выдавать диагностическое сообщение; отсутствующие данные не считать успехом
  проверки соответствия.
- Смена маппинга не должна изменять историю предыдущих запусков.

Сначала проверить доступные поля реальных trace и расширить парсер под них.
Не заявлять наблюдаемость фактической модели, которую хост не предоставляет.

## 6. Проверки

Обновить `tests/Idd.Generation.Tests/FactoryExecutionPolicyContractTests.cs`:
обязательный профиль, отсутствие default, полный маппинг, явный inherit,
повторная настройка, перечитывание перед запуском, точная передача overrides.
Проверить и канонические источники, и сгенерированные инструкции платформ.

Добавить trace fixtures и тесты в `tests/Idd.Factory.Report.Tests`:

- Три профиля корректно связаны с настройками своих worker.
- Одна модель используется для разных профилей с разным reasoning.
- Отсутствующие данные о фактической модели остаются неизвестными.
- Подтверждённое расхождение настроек отражается в диагностике.
- Обновление маппинга не меняет данные предыдущего запуска.

Расширить `tests/Idd.Factory.LiveTests` целевыми сценариями на хосте,
поддерживающем per-child overrides:

1. Заданный профиль приводит к точным model/reasoning в нативном spawn.
2. Изменение политики между двумя последовательными запусками применяется
   ко второму worker; первый сохраняет прежние настройки в отчёте.
3. Отсутствующий/неизвестный профиль и неполная конфигурация блокируют spawn.
4. Отклонение модели не вызывает автоматический запуск на другой модели.

Для сценариев маршрутизации использовать контролируемые задачи с заданными
профилями: не полагаться на случайную классификацию сложности планировщиком.
Сценарий обновления должен менять политику снаружи worker; worker её не редактирует.
Конкретные доступные модели задаются настройками live-eval, а не каноническими
рекомендациями. Если хост не сообщает фактическую модель, live-тест проверяет
параметры spawn и явно фиксирует предел этой проверки.

Тесты текста инструкций подтверждают контракт, но не исполнение хостом;
проверки trace и live-сценарии необходимы для проверки применения настроек.

## 7. Документация и завершение

Обновить `docs/factory-workflow-configuration.md`, связанные Factory workflow
и skill docs, `docs/factory-report.md` и README live-тестов. Найти и убрать
противоречащие формулировки про optional профиль, default `standard`, partial
mapping и неявный inherit в других канонических материалах. Согласовать
актуальные durable Intent документы проекта при необходимости.

Выполнить генерацию и штатные проверки репозитория, тесты генерации и отчёта,
затем целевые live-сценарии. Сгенерированные файлы обновлять генератором.

## Критерии готовности

- Каждая задача содержит ровно один допустимый профиль.
- В режиме маппинга worker получает точные настройки назначенного профиля.
- Отсутствующая или некорректная конфигурация и отклонённый override не
  приводят к неявной подмене модели.
- Повторная настройка позволяет заменить модели без изменения профилей.
- Новый маппинг применяется к следующим worker без перепланирования.
- Отчёт различает запрошенные настройки, подтверждённые фактические настройки
  и отсутствие данных; история предыдущих запусков сохраняется.
- Явное использование модели сессии остаётся отдельной понятной стратегией.
