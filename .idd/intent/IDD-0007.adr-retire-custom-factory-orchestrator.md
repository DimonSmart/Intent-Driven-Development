# IDD-0007.adr-retire-custom-factory-orchestrator

## Status

Accepted

## Context

The original Factory idea was intentionally small.

A large implementation request should not remain in one continuously growing agent
context. Factory should repeatedly decompose current work, execute small tasks in
fresh contexts, then reassess the repository:

```text
request
-> planner
-> small tasks
-> fresh worker per task
-> planner
-> ...
-> done
```

The main purpose was context management:

- keep individual semantic contexts small;
- allow bounded tasks to use cheaper models where appropriate;
- avoid requiring a complete up-front implementation roadmap;
- let later planning use repository changes produced by earlier work.

The repository and durable IDD intent were expected to hold long-lived product
and implementation reality. Factory itself was expected to remain thin.

During early implementations, however, a practical execution problem appeared.
When a parent agent started a long-running worker or command, control could
return to the parent before the child had finished. The parent then spent model
turns polling:

```text
start worker
-> status
-> wait
-> status
-> wait
-> status
...
```

Those turns consumed tokens without performing useful semantic work. The longer
the child operation ran, the more orchestration overhead the parent could
accumulate.

To remove that waste, Factory introduced a programmatic orchestrator. A .NET
runtime took ownership of waiting and execution mechanics, and an MCP transport
later provided a blocking call boundary so the parent model did not need to poll.

This solved a real problem:

> Elapsed execution time should not by itself increase parent-agent token cost.

At the time, moving execution waiting out of the model was a reasonable
architectural experiment.

## How the experiment evolved

Once Factory had its own runtime, more operational responsibilities naturally
moved into it.

The runtime eventually owned concepts such as:

- authoritative workflow state;
- explicit state transitions;
- persisted continuation;
- semantic attempts;
- technical restarts;
- retry budgets;
- process supervision;
- cancellation;
- verification lifecycle;
- final verification;
- verification evidence;
- changed-path tracking;
- backend failure classification;
- blockers and recovery;
- schema versions and legacy-run handling;
- progress reporting;
- MCP lifecycle;
- finalization.

The architecture therefore evolved from:

```text
planner
-> tasks
-> workers
-> planner
```

toward:

```text
semantic agents
      |
      v
deterministic workflow runtime
      |
      v
persistent state machine
      |
      v
process supervision
      |
      v
verification and recovery
      |
      v
transport layer
```

The resulting runtime was internally coherent and provided stronger execution
guarantees. It also became a substantial workflow system whose complexity was
much broader than the original Factory problem.

## Experiment results

### Blocking execution was the right requirement

The original polling problem was real.

A long-running worker must not require a parent LLM to repeatedly spend turns
asking whether execution has finished.

This requirement remains valid after the custom runtime is removed.

### The semantic/mechanical boundary was useful

The experiment reinforced an important IDD rule:

```text
semantic decisions -> agents
mechanical operations -> deterministic mechanisms
```

For example, deciding which durable intent documents materially constrain a
task is semantic work. Resolving those selected IDs and supplying the
corresponding documents to a worker is mechanical work.

The removal of the custom runtime does not change this distinction.

### Exact workflow recovery has a high architectural cost

Once Factory tries to know exactly which semantic attempt is active, whether a
failure was semantic or technical, whether a process may have partially
completed, which transition is legal next, which evidence belongs to which
attempt, and how an older persisted schema can resume, Factory becomes a durable
workflow engine.

Those guarantees are valuable when durable workflow execution is itself the
product. They are not necessary for Factory's primary purpose of splitting
coding work across fresh semantic contexts.

### Repository reality is more useful than exact execution history

After an interrupted implementation task, the most useful recovery question is
usually not which internal Factory transition happened last. It is what the
repository looks like now.

A fresh worker can inspect current repository reality and finish the requested
task. This allows Factory to rely on semantic convergence instead of
reconstructing the exact internal state of a previous worker execution.

### At-least-once semantic execution is sufficient

Factory does not require exactly-once task execution.

If a worker is interrupted after partially changing the repository, a fresh
worker may execute the same task again with explicit instructions to inspect
the current workspace first and complete only what remains.

This model intentionally trades exact execution history for simplicity:

```text
at-least-once execution
+
repository inspection
+
semantic convergence
```

For the intended use case, this is sufficient.

## Why the custom orchestrator is no longer justified

The programmatic orchestrator was introduced primarily because efficient
blocking delegation to isolated agents was not available at the platform level.

Supported coding-agent hosts can now provide native child-agent execution,
fresh or isolated contexts, shared repository access, and blocking or
event-driven waiting.

The original useful property:

```text
do not spend model turns polling a worker
```

can therefore be obtained without Factory maintaining its own workflow runtime,
process supervision, state machine, and MCP transport.

The architectural trade-off has changed. Keeping the custom orchestrator would
preserve substantial complexity after its main original justification has
disappeared.

## Decision

Retire the custom Factory orchestrator.

Factory returns to its original role: a lightweight semantic orchestration layer
over ordinary isolated agents.

The current target architecture is defined normatively by IDD-0006.

Conceptually it is again:

```text
request
-> fresh planner
-> currently contractable tasks
-> fresh worker per task
-> fresh planner
-> Tasks | Question | Done
```

Native platform mechanisms own child-agent creation, isolation, waiting, and
completion signaling.

Factory does not recreate those facilities through a dedicated .NET runtime or
MCP server.

If a platform cannot provide suitable native isolated-agent execution, Factory
may be unsupported on that platform rather than reintroducing a universal
workflow runtime solely for adapter parity.

## Recovery model

Factory persistence is scheduling assistance, not an authoritative replayable
execution log.

The durable sources of reality remain:

```text
.idd/intent = durable product intent
repository  = implementation reality
```

Temporary Factory artifacts may preserve the original request, current tasks,
short completed-task summaries, user answers, and a pending question.

When execution is interrupted, Factory may rerun the unfinished task in a fresh
context. The worker must assume previous execution may have partially changed
the repository and inspect current reality before continuing.

Factory does not restore the previous process, resume its internal reasoning, or
reconstruct an exactly-once execution boundary.

## Verification model

The experiment also showed that Factory does not need to own a separate
verification workflow engine.

Workers can perform focused verification while implementing their tasks.

Repository-level IDD verification may run when planning reaches `Done`. If it
fails, bounded failure evidence becomes input to another fresh planner cycle.

Verification failure is therefore semantic evidence for replanning rather than
a reason to recreate a specialized Factory transition and recovery subsystem.

## Consequences

The .NET Factory runtime, Factory-specific MCP transport, process supervision,
workflow state machine, retry/restart machinery, verification lifecycle, and
runtime schema are no longer part of the target architecture.

This deliberately reduces implementation size, maintenance cost, test surface,
adapter coupling, migration burden, Factory-specific execution protocol, and
opportunities for orchestration mechanics to consume semantic context.

The trade-off is explicit. Factory no longer promises exact continuation of an
interrupted semantic execution. A task may run more than once.

Workers must therefore be repository-aware and tolerate partial prior execution.

This is preferable to maintaining a durable workflow engine for the intended
Factory use case.

## Architectural lesson

The custom orchestrator was not a failed implementation. It was an experiment
that isolated a real problem and clarified which guarantees Factory actually
needs.

The lasting requirements are:

- fresh contexts for bounded semantic work;
- incremental replanning from current reality;
- no model-driven polling while workers run;
- semantic decisions remain with agents;
- deterministic bookkeeping remains mechanical.

The lasting non-requirement is ownership of a general-purpose durable workflow
platform.

Factory exists primarily to manage semantic context boundaries, not workflow
infrastructure.
