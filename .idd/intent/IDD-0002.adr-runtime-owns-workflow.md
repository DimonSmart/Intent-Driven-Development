# IDD-0002.adr-runtime-owns-workflow

## Status

Accepted

## Context

Factory must execute large tasks whose later work can be unknowable until earlier work produces repository changes, evidence, or semantic findings. The previous architecture improved determinism by moving orchestration from an LLM coordinator into .NET, but still represented execution through a second predefined workflow graph such as `decompose -> execute -> replan -> review -> finalize`.

That second graph duplicates information already present in task state. Whether work can execute, needs refinement, needs verification, is waiting on a dependency, requires global restructuring, or is ready for final review can be derived from the persisted task graph plus deterministic policy. Keeping a separate workflow machine makes recovery and evolution harder and encourages semantic results to be expressed as workflow routing rather than changes to the actual task.

## Decision

The .NET 10 Factory runtime is the sole owner of operational decisions. Its primary and only substantial execution graph is the dynamically evolving graph of the user's task.

The runtime uses a pure deterministic scheduler over authoritative persisted state. It decides which of the following concrete operations is applicable: initial decomposition, scoped refinement of an outline, dispatch of ready work, authoritative verification, bounded global replan, materialization/dispatch of final semantic review, finalization, or a structured stop. No LLM chooses a workflow step.

Task graph nodes carry a required capability once executable. Capability is a semantic work type, not an agent identity. Runtime maps capabilities to registered role/skill/execution-profile contracts. Workers cannot invent arbitrary roles or skills and cannot choose the next capability to execute.

Initial decomposition is intentionally allowed to be partial. Known future scope may be persisted as `outline` and refined only after dependencies provide the information needed to create a safe executable contract. Workers may also report a typed `additional-work-required` requirement. Runtime validates it, materializes a new graph node, persists the dependency, and later resumes the source work with the dependency result. A separate semantic replanner is reserved for genuine global strategy changes that cannot be represented by local graph growth or scoped refinement.

Task-graph topology and definitions are versioned by `GraphRevision`. Ordinary runtime state saves use a separate CAS `Revision`. A graph mutation validates a complete candidate before authoritative state changes. Completed work is immutable. Contract revisions are immutable artifacts. Append-only graph-mutation records are diagnostic provenance only and are never replayed to reconstruct state; `state.json` is authoritative.

Verification remains a deterministic runtime responsibility. Intermediate work may persist explicit per-check expectations (`must-pass` or `may-fail`). A failed check is an expected intermediate RED only when every failed check is explicitly `may-fail`; otherwise it is an unexpected regression. Final verification is always strict. Successful deterministic verification never invokes an LLM classifier or hidden verification-fix worker.

Semantic review is work in the task graph, not a special workflow state. A review that finds a local defect completes as evidence and causes runtime to materialize corrective graph work. After correction, the required review is represented by a fresh review node. Final integrated review remains mandatory for successful completion.

Factory configuration is policy-only. The packaged/project `factory.yaml` may configure bounded limits, mandatory final-review policy, and the allow-list of registered work capabilities. It does not describe steps, transitions, handlers, or a second execution graph. The effective configuration hash is pinned to a run.

Factory Core depends on an agent-backend abstraction. Codex CLI remains the first production backend. Backend adapters expose the selected skill and map execution profiles to platform permissions; they do not own scheduling or graph mutation.

## Alternatives Considered

- Keep the deterministic .NET workflow state machine: rejected because it duplicates the task graph and forces dynamic discoveries through artificial phase transitions.
- Restore an LLM coordinator: rejected because operational decisions are derivable from typed state and deterministic policy.
- Treat every discovery as global replanning: rejected because local prerequisites and deferred detail can be represented directly in the graph with less semantic work and better provenance.
- Build a generic workflow/DAG framework: rejected because Factory needs a bounded domain runtime, not a general orchestration product.
- Replay event or graph history for recovery: rejected because one authoritative crash-safe state snapshot is simpler and avoids ambiguity after partial writes.
- Parallel implementation workers in V1: deferred; safe parallelism requires separate worktree/merge/integration architecture.

## Consequences

- There is no persisted `CurrentWorkflowStep`, workflow transition table, workflow name/hash, or packaged `factory-workflow.yaml`.
- `GraphRevision` is the durable task-graph generation; `Revision` remains the state-store concurrency revision.
- Factory can execute tasks that cannot be planned fully in advance.
- Semantic agents are smaller and more isolated: they implement, research, review, refine, or propose global restructuring, but never coordinate runtime phases.
- Runtime tests must cover scheduler determinism, graph mutation atomicity, dynamic dependencies/refinement, expected RED classification, strict final verification, review correction, and crash recovery without history replay.
- Legacy active runs using the previous state schema must finish with the previous Factory version or be cancelled and restarted.
- New backends can be added without changing task-graph semantics, verification, or scheduling policy.

## Supersedes

The workflow-composition portion of the previous accepted version of this ADR. Durable runtime ownership remains; the owned operational model is now the dynamic task graph rather than a predefined workflow machine.
