# IDD-0006.adr-native-agent-factory-orchestration

## Context

Factory decomposes a large implementation request into bounded semantic tasks
executed in fresh child contexts. The essential responsibility is to manage
context boundaries and incrementally reconsider the current repository, not
to provide a durable workflow engine.

Factory requires efficient waiting: elapsed worker execution time must not
cause repeated token-consuming parent-model status polls. Supported coding-agent
hosts can provide isolated native child agents, shared repository access and
blocking or event-driven terminal waiting.

## Decision

Factory uses native platform subagents and lightweight orchestration, not a
custom deterministic .NET runtime or Factory-specific MCP/CLI transport.

```text
complete request -> preflight -> fresh planner
-> contractable task batch -> fresh isolated worker per task
-> fresh planner -> Tasks | Question | Done
```

Each planner and worker uses a fresh semantic context without parent transcript
inheritance; workers receive focused task contracts. Native host primitives own
child creation, isolation, waiting, terminal result retrieval and stop/close.
Blocking or event-driven waits are mandatory: no model-driven polling loop.
A platform without these capabilities may leave Factory unsupported rather
than recreating a universal workflow/process runtime for parity.

Semantic judgments, including task decomposition, new plans and relevant
`TaskRelatedIntent` or Conditional Engineering selection, belong to agents.
Mechanical ID resolution, Always Engineering propagation and temporary
bookkeeping belong to deterministic operations.

Current repository contents are authoritative implementation reality;
`.idd/intent/` holds durable product and architecture decisions. Factory's
temporary Markdown request, plan, answers and bounded summaries are scheduling
and context aids, not an authoritative replay log, durable state machine or
exact continuation protocol.

Factory deliberately offers **at-least-once semantic execution**. A task
interrupted after partial repository changes can be retried by a fresh worker
which inspects and preserves correct prior work. Semantic convergence from
current repository reality is preferred to reconstructing precisely which
attempt or process transition last occurred. An untrusted or failed native
terminal wait leaves the task pending, stops or closes the child where possible,
and ends the current invocation; native platform failures are not translated
into an invented Factory backend-retry state.

Workers perform focused local checks. After planner `# Done`, configured
project-level verification runs; bounded failure evidence may prompt a fresh
planner. Factory does not implement its own verification lifecycle, semantic
retry budgets or process supervision.

## Experiments and Findings

An earlier deterministic .NET orchestrator was introduced to solve a genuine
problem: parents spent expensive model turns polling long-running workers.
The experiment established that **blocking execution is a requirement**,
regardless of the transport used to provide it. A packaged MCP blocking
transport and CLI delegation satisfied the wait requirement while the runtime
existed, but neither is necessary when native child-agent waiting is available.

Once the runtime owned waiting, it accumulated authoritative workflow state,
persisted attempts and continuation, retries, process supervision, backend
failure classification, verification transitions and schema migrations.
Exactly replaying semantic attempts is complex and fragile when a worker may
have changed the repository before an interruption. These guarantees are
valuable for a workflow execution product, but are not necessary for Factory's
context-isolation purpose.

The experiment also confirmed that semantic decisions and mechanical operations
should have separate owners. Exact stable-ID resolution and waiting need no
reasoning; choosing a task's relevant constraints and replanning after changed
repository reality do. Keeping each child isolated reduces accumulated context
and can permit appropriate lower-cost worker models. Incremental planning
avoids pretending to know an entire implementation roadmap in advance.

## Alternatives Considered

- **Custom durable workflow runtime:** supplies stronger process/state recovery
  and centralized retries but creates a large independent workflow platform,
  operational complexity, state migrations and adapter coupling.
- **Blocking transport around that runtime:** prevents expensive polling but
  retains the runtime and custom MCP/CLI integration once host-native waits can
  supply the same important property.
- **Exact-once and exact-continuation semantics:** require knowledge of partial
  external side effects that cannot safely be inferred from task state alone.
  At-least-once execution with repository inspection is appropriate here.
- **Model-driven status polling:** rejected because the number of parent
  inference turns grows with worker duration without useful semantic progress.

## Consequences

Factory is deliberately smaller: no dedicated .NET orchestration runtime,
Factory-specific MCP transport, persistent workflow state machine, custom
backend failure taxonomy, process supervisor or exact recovery guarantees.

Host support depends on native spawn, isolated contexts, shared workspace,
non-polling wait, trusted terminal result and stop/close controls. Older
runtime state is not exactly resumable; repository effects remain and an
explicit fresh start can reuse an appropriate persisted request.

The tradeoff is occasional re-execution of unfinished work, so workers must
inspect current repository reality and tolerate partial prior execution.
Final verification remains part of the surrounding IDD workflow without
creating a separate Factory verification engine.

The behavioral contract and precise lifecycle are owned by the current
`IDD-0001` specification; this ADR explains why those architectural
boundaries and guarantees were chosen.
