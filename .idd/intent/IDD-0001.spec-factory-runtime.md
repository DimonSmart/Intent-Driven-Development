# IDD-0001.spec-factory-runtime

## Intent

IDD Factory executes a complete implementation request through a deterministic, resumable .NET runtime. The runtime owns operational decisions while fresh semantic agents perform only work that requires understanding requirements, intent, architecture, implementation meaning, research, or semantic correctness.

The dynamically evolving graph of the user's task is the primary execution graph. Factory does not require or persist a second global phase machine such as `decompose -> execute -> replan -> review -> finalize`.

## Core Behavior

- The public Factory entry point accepts the complete user request and invokes a packaged Factory runtime for the selected workspace.
- The canonical Factory entry skill defines transport-neutral run, continue, clarification, cancellation, and outcome-reporting behavior. Platform adapters supply launcher mechanics without changing runtime semantics.
- The generated Codex Factory plugin exposes its packaged runtime through its supported blocking transport. One explicit Factory invocation maps to one runtime invocation; the launcher does not coordinate semantic workers, poll a workflow machine, or mutate Factory state.
- The original request is stored as an immutable run artifact. It is available to decomposition, genuine global replanning, intent handling, and final integrated review. Ordinary work receives its own immutable self-contained contract plus focused dependency/result context.
- Every semantic operation runs in a fresh isolated context. Conversation transcripts and event streams are diagnostics and are never required to resume or recover a run.
- Runtime selects a registered semantic capability, maps it to a logical role, canonical Factory skill, and backend-neutral execution profile, then supplies only the focused dynamic input. Backend adapters own skill activation and permission/sandbox mechanics.
- A Factory skill is the complete semantic contract for its role/capability. Runtime does not compose hidden coordinator prompts or use another LLM to choose the next operational action.

## Dynamic Task Graph

- Initial decomposition produces the smallest safe graph needed to make progress. It is not required to predict the complete task.
- A work definition is either `Executable` or `Outline`. Executable work has a registered capability and a self-contained immutable contract. Outline work records known future scope whose exact executable contract depends on earlier results.
- Runtime may refine an outline after its dependencies complete. Scoped refinement is local: it may make the same node executable or replace it with a small subgraph. It does not globally rewrite unrelated remaining work.
- Executable capabilities are registered runtime concepts such as `implementation`, `research`, `documentation`, and `semantic-review`. A capability describes required work; it is not a worker-selected role or skill name.
- Runtime deterministically promotes work whose dependencies are complete and dispatches ready work according to stable sequence/ID ordering. Dependency edges, not a global workflow step, express prerequisite order.
- A worker that discovers a concrete missing prerequisite returns `additional-work-required` with a typed capability/goal/reason requirement. Runtime validates the requirement, materializes a new graph node, adds the dependency, persists provenance, and later resumes the source work with the dependency result.
- A worker returns `global-replan-required` only when the remaining global strategy is invalid and local graph growth/refinement is insufficient. Global replanning is bounded, read-only, proposal-based semantic work. Runtime validates and atomically applies only supported mutations to mutable remaining work.
- Completed work is immutable. It cannot be removed, redefined, reordered as mutable work, or silently reopened by decomposition, correction, or replan.
- Semantic review is graph work. Selective reviews may be present in decomposition; final integrated semantic review is materialized by runtime when ordinary product work is quiescent and remains mandatory for success.
- A review finding is durable evidence. A local defect returns a typed correction requirement; runtime materializes corrective work rather than asking the reviewer to edit the product. After correction, a fresh required review node is used.

## State, Revisions, and Persistence

- Authoritative run state is JSON under `.idd/factory/current/state.json`.
- `Revision` is the monotonically increasing compare-and-swap state revision used for crash-safe single-writer persistence.
- `GraphRevision` changes only when task-graph topology or a work definition changes. Ordinary lifecycle/status/evidence persistence does not advance it.
- Work-item contract revisions are immutable artifacts under `.idd/factory/current/work-items/.../contracts/`. A changed definition creates a new contract artifact; previously referenced contract content is never overwritten.
- Before graph mutation, runtime builds and validates the complete candidate graph: unique IDs/sequences, registered/allowed capabilities, references, cycles, verification IDs, immutable completed work, lifecycle legality, and graph-revision rules.
- Only after candidate validation may runtime persist new immutable contracts/diagnostic mutation provenance and then atomically save the authoritative state snapshot.
- Append-only graph-mutation records under `.idd/factory/current/graph/` are diagnostic provenance. They are not an event-sourced authority and are never replayed to reconstruct state. A crash may leave orphan diagnostic/immutable artifacts; recovery follows `state.json` and may safely retry.
- State schema, Factory configuration schema/hash, worker protocol version, verification policy, runtime version, and methodology version are independent compatibility dimensions.
- Active state from an incompatible previous schema is reported as legacy/unsupported. It is not guessed, replayed, or silently migrated; the run must finish with the previous runtime or be cancelled/restarted.

## Deterministic Scheduler

Runtime derives the next operation from authoritative state. Conceptually it can select only concrete domain operations:

- initial decomposition when no task graph exists;
- exact continuation of a persisted semantic or verification operation;
- authoritative verification for work awaiting verification;
- scoped refinement for a dependency-ready outline;
- dispatch of dependency-ready executable work;
- bounded global replan when a persisted global trigger exists;
- strict final verification after ordinary product work reaches quiescence;
- materialization of mandatory final semantic review after strict final verification succeeds;
- dispatch of the current final review;
- deterministic finalization when all completion predicates hold;
- structured stop when no safe operation is applicable.

There is no `CurrentWorkflowStep`, transition table, workflow name/hash, or semantic next-step coordinator in authoritative state.

## Verification

- Authoritative verification executes only in runtime from stable check IDs and deterministic project/platform policy.
- Semantic workers do not decide whether a runtime check passed and do not run hidden verification-fix cycles. Successful deterministic verification causes no semantic classification call.
- Each executable work item may persist per-check intermediate expectation `must-pass` or `may-fail`.
- An intermediate verification failure is `ExpectedFailure` only if every failed check is explicitly `may-fail` for that work item. An unspecified or `must-pass` failed check is `UnexpectedFailure`.
- Expected intermediate RED may complete the current work item because the graph contract explicitly anticipated it. Evidence is retained for dependent work and later review.
- Unexpected verification failure blocks the run unless a separately represented graph correction/replan semantics exists. Runtime does not hide an LLM repair loop behind verification.
- Final verification is always strict. `may-fail` never weakens final completion requirements.
- Existing valid `.idd/verification.yaml` remains authoritative. A malformed existing policy is an explicit error and is never replaced by fallback. Absence of the file is a supported fallback mode; workers invent no stable IDs in that mode.
- Verification evidence records the actual check definition, execution time, result/status, and available output/evidence references from the current workspace. Ordinary Factory execution does not claim product-workspace transaction isolation or content snapshot reproducibility.
- Confirmation-required and manual checks persist exact continuation state and require explicit user input before runtime proceeds.

## Semantic Workers and Protocol

- Semantic result envelopes are versioned, attempt-specific, and authoritative only when protocol version, run ID, attempt ID, role, and allowed outcome validate.
- Free-form stdout is diagnostic, not authoritative result state.
- Runtime persists an exact continuation descriptor before dispatch. A resumable stop can continue that exact operation; runtime never invents a generic semantic continuation with no operation identity.
- Implementation/documentation workers may return `completed`, `additional-work-required`, `global-replan-required`, durable-intent/user blockers, or external blockers.
- Research is a read-only capability that returns focused findings or typed discovered work without modifying product state.
- Review workers may return `approved`, a typed correction/additional-work requirement, a genuine global replan requirement, or blockers. Reviewers never implement fixes themselves.
- Decomposer/scoped-refinement workers return graph definitions/proposals only. Replanner returns mutation proposals only. Runtime remains the sole graph-state writer.
- Workers cannot select arbitrary roles/skills/capabilities. Runtime validates every executable node against the registered capability catalog and the pinned Factory capability allow-list.
- Read-only semantic roles are constrained through execution profiles. Factory protects its state, request, contracts, graph provenance, Factory policy, durable intent, and verification policy from worker mutation.

## Recovery and Attempts

- Semantic dispatch persists attempt identity and invocation metadata before backend execution.
- Recovery uses authoritative state plus attempt invocation/result/process/workspace-change evidence. It never asks an LLM to reconstruct orchestration and never replays the event or graph history to infer current state.
- If authoritative state contains an active attempt but `attempts/<id>/invocation.json` is absent, semantic dispatch is known not to have begun. Runtime clears the active attempt, returns the work item to retryable state, and retries the exact persisted operation.
- If `invocation.json` exists but `result.json` is absent, the attempt is treated as interrupted. For workspace-write execution, runtime recovers persisted workspace-change evidence, clears the active attempt, returns the work item to retryable state, and retries the exact persisted operation.
- If both `invocation.json` and `result.json` exist, runtime validates attempt/result identity and protocol, recovers workspace-change evidence when applicable, and consumes the persisted result without redispatching that semantic worker.
- Workspace-write attempts record focused workspace-change evidence so later work/review can understand actual product changes without treating Factory diagnostics as product changes.
- Cancellation preserves product changes and diagnostic artifacts. Explicit cancellation and transport interruption remain distinct semantics.
- Every semantic attempt distinguishes clean exit, forced termination after an accepted complete result, cancellation, and transport failure; actual process exit semantics are not synthesized.

## Final Review and Finalization

- Final integrated semantic review is mandatory and is represented as a persisted `semantic-review` graph node.
- Runtime reaches ordinary product-work quiescence and passes strict final deterministic verification before it materializes the current final-review node.
- Materializing the read-only final-review node advances `GraphRevision`; runtime carries the just-passed final-verification provenance forward to that read-only revision and does not rerun an otherwise identical full verification solely because the review node was added.
- A final review defect completes the review node as immutable evidence and materializes corrective graph work. Any later product/corrective graph mutation makes prior final-verification and final-review completion stale; after correction runtime reaches quiescence, runs a fresh strict final verification, materializes a fresh final-review node, and reviews again.
- Successful finalization requires no active semantic attempt/verification session/continuation, no incomplete required graph work, strict final verification for the current `GraphRevision`, and approved final review for the same revision.
- Finalization creates and validates result artifacts before clearing `.idd/factory/current`. Results include current graph revision/configuration provenance, work-item contracts/results, verification evidence, attempts, graph-mutation diagnostics, audit events, and commit-message material. Existing result directories are preserved with collision-safe suffixes.

## Factory Configuration

- The packaged default `factory.yaml` is policy-only. A workspace `.idd/factory.yaml` may override supported policy.
- Supported configuration includes bounded attempt/replan/corrective/work-expansion limits, mandatory final-review policy, and allow-listed registered work capabilities.
- Configuration must not define workflow steps, transitions, handlers, arbitrary roles, scripts, or a second DAG.
- The effective Factory configuration hash is persisted at run creation. A changed effective configuration during an active run is reported rather than silently adopted.
- Non-negotiable safety invariants cannot be weakened by project configuration; final integrated review remains mandatory in this version.

## Budgets and Stops

- Agent attempts, global replans, corrective cycles, and graph expansion have explicit deterministic bounds.
- Budget exhaustion is a structured terminal condition for the pinned run; it is not hidden retry/replan behavior.
- Clarification, intent-required, verification action, external blocker, and protocol failures retain exact reason/payload/provenance across state and transport where resumability is safe.
- A stopped run never changes status alone to resume. `continue` either resolves the persisted exact continuation or reports that the run cannot be resumed safely.

## Durable Architecture and Constraints

- Production runtime targets .NET 10 and is packaged with Factory plugins; project-local runtime installation is not required.
- Factory CLI `run`, `continue`, and `cancel` remain complete interfaces. Adapter transports return the same structured outcomes and do not add transport concepts to persisted state.
- Operational state uses atomic filesystem JSON for the single-run/single-writer V1 model. SQLite, generic scripting, arbitrary shell DSL, dynamic code loading, generic workflow primitives, and parallel implementation workers are outside this runtime.
- Factory does not fingerprint, lock, or snapshot the entire product workspace in ordinary execution. Exact source revision/reproducibility remain controlled-workspace or release concerns.
- Backend-specific model flags, reasoning options, skill activation/discovery, sandbox and capability-isolation mechanics remain adapter/evaluation concerns; Factory Core does not encode Codex CLI syntax.
- Project/domain skills may be available to semantic workers. User-global skill inheritance is explicit capability policy and fixed for controlled installed-plugin evaluation.

## Evaluation, Benchmarking, and Release

- Installed-plugin live evaluation uses the generated plugin/runtime from the supported marketplace lifecycle. Controlled evaluation propagates explicit model/reasoning configuration to every semantic worker and records requested/effective values when observable.
- Evaluation artifacts retain state-change progress and separate launcher, semantic-worker, and end-to-end token usage. The primary Factory total is end-to-end usage.
- Live evaluation verifies capability/skill identity, isolation, clean process termination on happy paths, actual runtime evidence, and absence of semantic coordinator agents.
- A repository benchmark runner may compare the same deterministic task across direct Codex, structured single-context work, isolated workers, Factory-selected decomposition replay, and the complete production Factory. Each iteration starts from an equivalent clean workspace and uses the same pinned acceptance contract/configuration.
- Benchmark reports retain raw successful/failed run data and summarize token, sequential-tool-batch, process, timing, correctness, and success-rate metrics as observed estimates rather than exact causal costs.
- Benchmark orchestration, workspace preparation, deterministic acceptance, and report generation are excluded from measured model token usage; agent/acceptance/end-to-end durations remain distinguishable.
- Deterministic repository checks build/test benchmark tooling without starting live model executions. Live benchmarks/evaluations require explicit invocation.
- Release publication is separate from live semantic evaluation. `publish-next-version.ps1` performs Git publication mechanics only. Tag-triggered publication validates the exact tagged revision deterministically before publishing marketplace artifacts/GitHub release.
- Real-LLM evaluation is never a release prerequisite. Codex host-lifecycle compatibility is evaluation evidence rather than a release invariant recreated for every version.

## Non-goals

- A general-purpose workflow/orchestration, CI, distributed scheduling, or visual workflow platform.
- A second global Factory workflow graph layered over the task graph.
- LLM selection of the next operational action.
- Event-sourced recovery or replaying conversations/history as Factory memory.
- Parallel implementation workers, worktrees, merge queues, or distributed leases in V1.
- Automatic product-intent editing by Factory workers.
- Requiring Claude support in V1.

## Acceptance Criteria

- A successful run can begin from a partial decomposition, execute dependency-ready work, refine outlines only when needed, and add newly discovered typed dependencies without requiring a complete initial plan.
- The deterministic scheduler's decision is a pure consequence of authoritative state/pinned policy; no persisted workflow step or semantic coordinator is required.
- Factory configuration contains policy/limits/capability allow-list only and cannot encode step transitions or arbitrary worker routing.
- Unknown/disallowed capabilities and invalid graph mutations are rejected before authoritative graph state changes.
- `GraphRevision` advances exactly once for graph topology/definition mutation and does not advance for ordinary status/evidence saves; `Revision` provides stale-write protection independently.
- Invalid cycles, dangling dependencies, illegal mutation of completed work, unknown verification IDs, and disallowed capabilities do not partially apply contracts, graph state, or counters.
- An orphan graph-history/contract artifact after a crash cannot become authoritative or require history replay; continuation uses `state.json` plus exact attempt evidence.
- Dynamic `additional-work-required` materializes a persisted dependency/result provenance and later resumes the source work after the new node completes.
- A genuine `global-replan-required` trigger is persisted and passed to the bounded global replanner; local discoveries do not require replanner invocation.
- Intermediate verification accepts expected RED only for explicitly `may-fail` failed checks; an unspecified/must-pass failure blocks as unexpected; final verification rejects all failed checks regardless of intermediate expectation.
- A green verification path invokes no semantic verification classifier/fixer.
- Review defects become explicit corrective graph work; completed review/work remains immutable; required follow-up review is a fresh graph node.
- Finalization occurs only after strict final verification and approved final integrated review for the current graph revision.
- Restart/cancellation preserve exact attempt evidence and reuse a persisted complete result without duplicate semantic dispatch; interrupted attempts follow the explicit retry semantics above and never require LLM/history reconstruction.
- Semantic clarification/intent/block outcomes retain structured reason/payload across persistence and transport when safely resumable.
- Final result artifacts/audit/verification/attempt/graph provenance correspond to actual execution and do not contain obsolete workflow-name/hash authority.
- State created through CLI can continue through adapter transport and vice versa without transport-specific state semantics.
- Core scheduling, validation, verification classification, graph mutation, recovery, correction, and finalization are testable with deterministic unit/integration tests and fake backends/clocks.
- Live evaluation continues to prove installed-plugin/runtime completeness, capability/skill identity, requested/effective execution configuration, process termination semantics, capability isolation, token aggregation, and absence of coordinator agents.
- Benchmark/release contracts remain deterministic and retain their existing explicit-invocation and publication separation.

## Verification

Automated tests cover scheduler determinism, state revisions and immutable completed work, capability/protocol validation, partial decomposition and scoped refinement, dynamic dependency insertion, candidate-graph atomic validation, crash recovery without history replay, deterministic expected-RED classification, strict final verification, semantic review corrections, global replans, finalization, cancellation, execution profiles, and protected-artifact ownership.

Live Factory evaluation additionally verifies real semantic capability topology, dynamic ordering/dependency behavior, review/correction evidence, worker execution configuration/termination semantics, installed-plugin lifecycle, capability isolation/skill identity, token aggregation, and absence of coordinator/workflow-step agents. Release validation remains deterministic and independent from live-model evaluation.
