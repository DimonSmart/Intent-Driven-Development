# IDD-0001.spec-factory-runtime

## Intent

IDD Factory executes a complete implementation request through a deterministic,
resumable .NET runtime. The runtime owns operational decisions while fresh
semantic agents perform only work that requires understanding requirements,
intent, architecture, implementation meaning, research, or semantic
correctness.

The authoritative execution model is an immutable completed history, zero or
one current task, and an ordered replaceable list of remaining work. Factory is
not a task-graph or general workflow engine.

## Core Behavior

- The public Factory entry point accepts the complete user request and invokes a
  packaged Factory runtime for the selected workspace.
- When a host represents text explicitly supplied with the request through a
  temporary pasted/attachment reference, the launcher mechanically materializes
  the exact supplied text before runtime creation. Host-local paths are
  transport metadata and are not durable Factory request semantics.
- The materialized logical request is self-contained and preserves user-authored
  text, whitespace, and Unicode exactly. Materialization does not summarize,
  paraphrase, infer, or expand arbitrary paths that were not explicitly supplied
  as request input.
- Request materialization is lossless. Invalid Unicode, U+FFFD replacement
  characters, or an unresolved known host-local pasted-text envelope prevent run
  creation rather than allowing corrupted or externally dependent request state.
- The canonical entry skill defines transport-neutral run, continue,
  clarification, cancellation, and outcome-reporting behavior. Platform
  adapters supply launcher mechanics without changing runtime semantics.
- The materialized logical request is stored as an immutable run artifact and is
  available to planning and final integrated review without requiring the
  original host-local attachment to remain available. Ordinary workers receive
  their own immutable task contract plus focused completed-work context.
- Every semantic operation runs in a fresh isolated context. Conversation
  transcripts and event streams are diagnostics and are never required for
  recovery.
- Runtime selects a registered semantic capability, maps it to a logical role,
  canonical Factory skill, and backend-neutral execution profile, then supplies
  only focused dynamic input.
- A Factory skill is the complete semantic contract for its capability. No LLM
  chooses the next operational action.

## Linear Work Model

- Authoritative state contains `Completed`, `Current`, and `Remaining` work.
  `Completed` preserves successfully verified work in completion order,
  `Current` contains at most one task, and `Remaining` is an ordered list whose
  first item always executes next.
- Completed work is immutable historical fact. Planning, replanning, retries,
  corrective work, and recovery cannot delete it, redefine it, reorder it, or
  return it to pending work. A discovered defect becomes new future work.
- Remaining work contains no cross-task references, dependencies, topology, or
  lifecycle status. Prerequisite order is expressed solely by list order.
- Runtime creates monotonic persistent work IDs, contract artifacts, attempts,
  and execution bookkeeping. Semantic planners provide no persistent IDs,
  sequences, statuses, revisions, or dependency metadata.
- Initial planning and later semantic replanning use one flat protocol: an
  ordered list of capability and task-contract pairs. Planning may return only
  the work currently knowable and need not predict the complete request.
- Runtime validates the complete planning result, creates IDs and immutable
  contracts, and atomically adopts the ordered list. A malformed or partially
  valid result leaves the authoritative plan unchanged.
- When completed work exposes further required work and no future work remains,
  runtime may invoke planning again with the new completed-work context.
- A worker that discovers a concrete prerequisite returns
  `additional-work-required`. Runtime ends the current attempt without
  completing its task and atomically prepends the prerequisite followed by the
  original task ahead of the existing remaining tail.
- A genuine strategy change may trigger bounded semantic replanning at a safe
  point. The replanner returns the complete ordered future suffix; runtime
  atomically replaces all remaining work and never changes completed history.
- Intermediate semantic review, when useful, is an ordinary ordered
  `semantic-review` task. Final integrated review remains a terminal
  orchestration phase rather than future plan work.

## State, Revisions, and Persistence

- Authoritative run state is JSON under `.idd/factory/current/state.json`.
- `Revision` is the monotonically increasing compare-and-swap state revision
  used for crash-safe single-writer persistence. A separate plan revision may
  exist only when required to invalidate final evidence and must describe the
  authoritative product/plan snapshot rather than graph topology.
- Planned work stores only semantic execution input and necessary
  attempt/recovery data. Verification evidence, results, and changed paths are
  execution evidence rather than planning structure.
- Completed records retain the contract, result, changed paths, and verification
  evidence needed for planner context, diagnostics, audit, recovery, and final
  review.
- Moving the first remaining task to current, moving verified current work to
  completed, prepending work, and replacing the remaining list are atomic state
  transitions.
- Immutable work contracts are written before the state that references them.
  An interrupted write may leave orphan diagnostic or contract artifacts, but
  recovery follows `state.json` and never replays history to reconstruct state.
- Optional plan-revision provenance records complete before/after remaining IDs,
  reason, and source attempt/result. They are diagnostics, not authoritative
  mutation operations.
- Active state from an incompatible previous schema is reported as unsupported;
  runtime does not guess a migration from an arbitrary active task graph.
  Product workspace artifacts from previous runs remain untouched.

## Deterministic Scheduler

Runtime derives the next operation from authoritative state:

- resume or stop for an exact persisted continuation or blocker;
- continue the exact operation for `Current` when present;
- move the first `Remaining` item to `Current`, persist, and execute it;
- when no current or remaining work exists, determine whether newly learned
  facts require more planning;
- run strict final verification, semantic final review, and deterministic
  finalization when the product work is quiescent;
- produce a structured stop when no safe operation applies.

The scheduler performs no dependency resolution, graph traversal, topological
readiness calculation, outline refinement, or arbitrary insertion/reordering.

## Execution and Verification

- A worker receives its immutable current contract, relevant completed
  work/results, relevant prior attempts and authoritative verification
  observations, and relevant repository state, not internal Factory state.
- After semantic completion, runtime selects and runs authoritative verification
  using actual changed paths and project policy. Verification is a
  post-condition of that semantic attempt. Only successful required
  verification permits the current task to move to completed history.
- An unexpected required-verification failure for the current task preserves the
  semantic result, changed paths, bounded diagnostic observations, and complete
  verification evidence; leaves the same task current; and makes it eligible
  for another ordinary semantic attempt. The next attempt receives the prior
  result and failed-verification observations through the normal work input.
- Retrying after failed intermediate verification uses the existing task
  capability, work-item execution operation, scheduler dispatch, attempt count,
  and configured semantic attempt budget. Runtime has no verification-fix
  operation, role, capability, counter, or hidden repair workflow, and the
  scheduler does not interpret verification commands or diagnostics.
- Semantic workers do not decide whether a runtime check passed and do not run
  hidden verification-fix cycles. Successful deterministic verification causes
  no semantic classification call.
- Expected intermediate failure is supported only as exceptional optional task
  metadata for a real configured use case and does not cause another semantic
  attempt. Final verification is always strict and does not automatically retry
  a historical implementation task.
- Existing valid `.idd/verification.yaml` remains authoritative. A malformed
  policy is an explicit error; absence is a supported fallback mode.
- Confirmation-required and manual checks persist exact continuation state and
  require explicit user input before runtime proceeds.

## Semantic Workers and Protocol

- Planning receives the materialized logical request, immutable completed-work
  summaries, the current trigger, and any existing future plan. It does not
  receive internal attempt, continuation, verification-session, or state
  topology data.
- Planning returns only `ready` plus an ordered `tasks` list. Each task contains
  a registered capability and a non-empty semantic contract. The first task is
  the first to execute.
- Runtime may perform bounded semantic repair after a malformed result but never
  guesses missing semantic intent.
- Worker outcomes remain semantic: completion, additional work required,
  genuine global replan required, blockers, and review findings as applicable.
- Worker results contain only the semantic outcome and its outcome-specific
  data. They do not contain run, attempt, work-item, role, capability, skill,
  execution-profile, result-location, or protocol identity already owned by
  runtime.
- Runtime binds every received semantic result to the invocation-specific
  backend channel, validates the result shape and outcome against the
  runtime-assigned capability and role, and only then creates the authoritative
  persisted attempt result from runtime-owned invocation identity.
- Planning uses the same trust boundary as every other semantic capability and
  returns its flat `outcome` and `tasks` body without an identity envelope.
- Runtime rejects semantic bodies that attempt to supply runtime-owned identity
  or bookkeeping. Such fields never select or alter the invocation to which a
  result belongs.
- Semantic-result schemas, persisted-attempt artifact schemas, backend
  transport versions, and Factory-state schemas are independently selected and
  versioned by runtime. A worker does not declare or imply any of those
  versions.
- Workers cannot select arbitrary roles, skills, or capabilities. Runtime
  validates every task against the registered catalog and configured allow-list.
- Read-only roles cannot mutate Factory state, durable intent, verification
  policy, or product files outside their execution profile.

## Recovery and Attempts

- Semantic dispatch persists attempt identity and invocation metadata before
  backend execution.
- Raw worker output is diagnostic and never authoritative before complete
  parsing and semantic validation. Malformed or disallowed output does not
  update authoritative Factory state.
- A validated attempt result is persisted atomically with provenance created
  only from the already-persisted invocation and backend-observed termination
  data. Runtime verifies that invocation and result artifacts belong to the
  authoritative current run, attempt, and operation before consuming them.
- Recovery uses authoritative state plus invocation, validated persisted
  result, verification, and workspace-change evidence. It never asks an LLM to
  reconstruct orchestration or recovers invocation identity from worker output.
- A selected current task survives a crash before worker start. A persisted
  valid worker result is consumed at most once without redispatch. Raw output
  alone is not consumed unless runtime deterministically revalidates it for its
  exact persisted invocation under an explicit recovery rule. Interrupted
  workspace-writing attempts recover change evidence and retry the exact task
  according to bounded policy.
- Verification continuation resumes the exact persisted session. A crash after
  verification success cannot cause a second completion commit or loss of the
  current task.
- Failed intermediate verification returns the current task to ordinary
  dispatchable execution without changing completed or remaining work, while
  retaining its prior semantic result, attempt count, changed paths, and both
  task-level and run-level verification evidence. Exhaustion remains governed
  by the ordinary semantic attempt budget and reports the latest useful
  verification diagnostics and full evidence reference.
- Prepend and full remaining-plan replacement are single authoritative commits;
  recovery observes either the old list or the complete new list.
- Cancellation preserves product changes and diagnostic artifacts. Explicit
  cancellation and transport interruption remain distinct semantics.

## Final Review and Finalization

- When current and remaining work are empty, runtime runs strict final
  deterministic verification followed by mandatory integrated semantic review.
- Final review is persisted separately from planned work. It receives the
  materialized logical request, completed history, results, verification
  evidence, and relevant workspace state.
- A review defect produces future corrective work. Completed work remains
  immutable; after correction runtime runs fresh final verification and review
  for the new product snapshot.
- Successful finalization requires no active attempt, verification session, or
  continuation; no current or remaining work; strict final verification for the
  current product snapshot; and an approved final review for that snapshot.
- Finalization creates and validates result artifacts before clearing
  `.idd/factory/current`. Existing result directories are preserved with
  collision-safe suffixes.

## Factory Configuration

- The packaged default `factory.yaml` is policy-only. A workspace
  `.idd/factory.yaml` may override supported policy.
- Supported configuration includes bounded attempt, replan, corrective, and
  work-expansion limits, mandatory final-review policy, and the allow-list of
  registered capabilities.
- Configuration does not define workflow steps, graph structure, transitions,
  handlers, arbitrary roles, or scripts. Non-negotiable safety invariants cannot
  be weakened.

## Durable Architecture and Constraints

- Production runtime targets .NET 10 and is packaged with Factory plugins;
  project-local runtime installation is not required.
- Factory CLI `run`, `continue`, and `cancel` remain complete interfaces.
  Adapter transports return the same structured outcomes and add no
  transport-specific state semantics.
- Operational state uses atomic filesystem JSON for a single-run/single-writer
  model. SQLite, event sourcing, generic scripting, arbitrary shell DSL,
  dynamic code loading, generic workflow primitives, and parallel
  implementation workers are outside this runtime.
- Factory does not fingerprint, lock, or snapshot the entire product workspace
  during ordinary execution.
- Backend-specific model flags, skill activation, sandboxing, and capability
  isolation remain adapter/evaluation concerns.
- Factory never creates or changes durable product intent.

## Evaluation, Benchmarking, and Release

- Installed-plugin live evaluation uses the generated plugin/runtime from the
  supported marketplace lifecycle and records requested/effective execution
  configuration when observable.
- Evaluation proves capability identity, isolation, process termination,
  sequential execution, recovery evidence, token aggregation, and absence of
  semantic coordinator agents.
- Benchmarks compare equivalent clean workspaces and distinguish orchestration,
  semantic-worker, acceptance, and end-to-end measurements.
- Release publication remains separate from live semantic evaluation. Real-LLM
  evaluation is not a release prerequisite.

## Non-goals

- A task graph, DAG, dependency solver, topological scheduler, or graph mutation
  framework.
- Outline work, scoped refinement, superseding/cancelling future nodes, or
  checkpoint-coverage mutation.
- A general-purpose workflow/orchestration, CI, distributed scheduling, or
  visual workflow platform.
- LLM selection of the next operational action.
- Event-sourced recovery or replaying conversations/history as Factory memory.
- Parallel implementation workers, worktrees, merge queues, or distributed
  leases in V1.
- Automatic product-intent editing by Factory workers.

## Acceptance Criteria

- A multi-step request executes strictly in remaining-list order with at most
  one current task.
- A request whose user-supplied text is represented by a temporary host-local
  pasted/attachment reference is materialized before runtime creation so
  `request.md` contains the exact supplied text and remains usable after the
  temporary source disappears.
- A known unresolved host-local pasted-text envelope, invalid Unicode, or U+FFFD
  in request text prevents creation of Factory run state.
- Materialization expands only explicitly supplied request inputs and does not
  reinterpret arbitrary paths appearing in the user's task.
- Successfully verified work moves once to immutable completed history and is
  unchanged by prepend, retry, repair, or full replanning.
- Planner output is valid with only an ordered list of capability and task
  pairs; runtime assigns all persistent identity and bookkeeping.
- Runtime can plan incrementally after completed research without materializing
  unknowable outline work.
- `additional-work-required` atomically yields prerequisite, original task, and
  old remaining tail in that order, with no dependency edge.
- Global replanning atomically replaces the complete remaining suffix and leaves
  the previous list authoritative if candidate validation fails.
- Authoritative runtime state and production scheduling contain no task
  dependencies, covered-work references, outline/refinement state, cycle
  validation, or graph revision semantics.
- Crash recovery preserves exact-operation semantics at task selection, worker
  result consumption, verification, completion commit, prepend, and plan
  replacement boundaries.
- Intermediate/manual verification, strict final verification, mandatory final
  review, corrective work, finalization, cancellation, and transport/backend
  isolation retain their behavior without graph nodes or edges.
- Unexpected required-verification failure for current work preserves its
  evidence and prior result, keeps the run active, and causes the ordinary
  scheduler to dispatch the same current task for another semantic attempt;
  expected intermediate failures and strict final failures retain their
  distinct semantics.
- Legacy active graph state is rejected explicitly rather than guessed or
  silently migrated.
- Semantic workers return no runtime-owned identity fields; final review,
  planning, research, implementation, and other capabilities all use the same
  semantic-result trust boundary.
- A persisted attempt result derives its run, attempt, role, capability, and
  work-item provenance only from the exact runtime invocation, cannot be
  consumed for another attempt, and is reused after interruption without
  redispatch or duplicate state application.
- Invalid, stale, cross-attempt, or identity-bearing semantic output never
  changes authoritative Factory state. Incompatible active persisted-result
  schemas are reported explicitly rather than interpreted as trusted current
  results.
- Core scheduling, state validation, planning, prepend/replacement, recovery,
  verification, review, and finalization have deterministic automated coverage.
- Current Factory documentation and canonical skills describe only the linear
  model.

## Verification

Automated tests cover lossless self-contained request materialization guards,
ordered initial planning and execution, immutable completed history, dynamic
prepend, atomic full replan, capability-specific semantic outcome validation,
rejection of runtime-owned fields, invocation and cross-attempt binding, atomic
validated-result persistence, raw-result trust boundaries, state and result
schema rejection, task selection and completion recovery without redispatch or
duplicate application, verification continuations, failed intermediate
verification retry with prior-result and bounded diagnostic context, ordinary
attempt-budget exhaustion, expected intermediate failure, strict final
verification, semantic review corrections, finalization, cancellation,
execution profiles, and protected artifact ownership.

Live Factory evaluation additionally verifies real sequential capability
execution, incremental planning, additional-work ordering, final review,
worker-process semantics, installed-plugin lifecycle, capability isolation,
token aggregation, and absence of coordinator agents.
