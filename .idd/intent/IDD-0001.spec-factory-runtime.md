# IDD-0001.spec-factory-runtime

## Intent

IDD Factory executes a complete implementation request through a deterministic,
resumable runtime. The runtime owns operational workflow decisions while fresh
semantic agents perform only work that requires understanding requirements,
intent, architecture, implementation meaning, or semantic correctness.

## Behavior

- The public Factory entry point accepts the complete user request and invokes a
  packaged Factory runtime for the selected workspace.
- The canonical Factory entry skill defines transport-neutral run, continue,
  clarification, cancellation, and outcome-reporting behavior. Each platform
  adapter supplies its own launcher mechanics without changing that semantic
  contract.
- The generated Codex Factory plugin exposes its packaged runtime through a
  bundled, directly visible, blocking MCP transport. One explicit Factory
  invocation maps to one transport call; the launcher does not poll, drive the
  runtime state machine, or silently fall back to shell execution when the MCP
  transport is unavailable. Other platform adapters may retain their supported
  packaged CLI launchers.
- The original request is stored as an immutable execution artifact and is
  available to decomposition, replanning, intent handling, and final integrated
  review. Implementers receive only self-contained Subtask contracts.
- Every semantic operation runs in a fresh isolated context. Conversation
  transcripts are diagnostic data and are never required to resume or recover a
  run.
- Semantic-worker execution records the requested model and reasoning effort,
  and records effective values when the backend can determine them. Explicit
  evaluation configuration is propagated to every semantic worker; an
  unconfigured production backend is reported as unpinned rather than inferred
  to match the launcher.
- For every semantic operation, the runtime selects a logical Factory role, its
  authoritative Factory skill, a backend-neutral execution profile, and only
  the dynamic input for that operation. The backend adapter makes the selected
  skill available and explicitly activates it using backend-specific mechanics.
- A Factory skill is the sole semantic contract for its role. The runtime does
  not read or combine installed skill files, separate role definitions, or
  Factory verification methodology into worker instructions. Workers remain
  free to discover and use relevant project and domain skills.
- Decomposition produces ordered, self-contained Subtasks and selective Review
  checkpoints. A final integrated review is mandatory for every successful run.
- The runtime determines the next workflow step, dependencies, activation,
  dispatch, verification, retries, checkpoints, replanning, final review, and
  finalization from typed state, repository evidence, verification evidence,
  and deterministic policy. A semantic coordinator is not part of normal
  execution.
- A review result that needs correction inserts a new corrective Subtask;
  completed work remains immutable and the affected review runs again.
- A semantic plan defect invokes a bounded factory-replanner. The replanner
  returns a versioned proposal and cannot mutate state, completed work, product
  intent, implementation, review results, or operational status. The runtime
  validates and applies only supported proposal operations.
- Authoritative verification runs only in the runtime from stable check IDs in
  project verification policy. Evidence is tied to the exact workspace
  fingerprint, including tracked, staged, and untracked content. Semantic
  workers do not leave diagnostic tool processes active after producing their
  result; implementation workers leave build and test execution to the
  immediately following authoritative runtime gate.
- An ordinary failed verification check is a structured workflow result rather
  than a verification-runner exception. The runtime may invoke the existing
  implementer capability in a bounded verification-fix mode and then reruns the
  same authoritative gate. Exhausting the per-gate fix budget blocks the run;
  runner infrastructure failures and checks requiring user action are not
  treated as implementation defects.
- Checkpoint and final semantic review occur only after the corresponding
  mandatory runtime verification gate passes. A successful gate causes no
  additional semantic invocation beyond the review already required by the
  workflow.
- Agent, replan, and corrective-cycle retries have explicit deterministic
  budgets. Exhaustion produces a structured non-success outcome.
- When a semantic worker stops the workflow, the runtime preserves the worker's
  exact non-empty reason and extensible structured payload in authoritative
  state and returns them unchanged through CLI and adapter transports. A
  clarification continued without an answer returns the same persisted details
  without invoking the worker again; an answer resumes the same run.
- Run state is authoritative filesystem JSON under `.idd/factory/current/`.
  State revisions prevent stale writes; durable transitions are persisted
  atomically before external side effects. An append-only event stream provides
  auditability but is not replayed to reconstruct state.
- Recovery uses persisted attempt identity, process and result evidence, and
  idempotent handlers. It does not ask an LLM to infer missing state and does not
  blindly duplicate dispatch.
- Cancellation stops an active backend process, preserves product changes and
  diagnostic artifacts, and does not clear state until termination is known.
- Cancelling an in-flight transport request terminates the transport-owned
  runtime process tree and leaves valid resumable Factory state. It is distinct
  from an explicit Factory cancellation request, which retains the existing
  persisted cancellation semantics.
- Every semantic attempt distinguishes clean exit, forced termination after an
  accepted complete result, cancellation, and transport failure. A complete
  semantic result may survive forced termination, but the attempt remains
  observably unclean and the actual process exit code is never synthesized.
- Finalization creates and validates result artifacts before clearing current
  state. Existing result directories are preserved and collisions receive a
  deterministic suffix.
- The runtime emits structured terminal or resumable outcomes and deterministic
  process exit codes.
- Release evaluation installs the generated Factory plugin through the
  supported Codex marketplace lifecycle and runs the packaged skill and runtime
  from the installed plugin instance. Release evaluation uses a controlled
  capability profile, exposes the selected Factory skill unambiguously, and
  does not inherit incidental user-global skills.
- Evaluation artifacts retain live state-change progress and separate launcher,
  semantic-worker, and end-to-end token usage. The primary Factory total is the
  end-to-end total.
- A repository benchmark runner compares the same deterministic implementation
  task across direct Codex, single-context structured work, isolated workers,
  replay of Factory-selected decomposition, and the complete production Factory
  workflow. Every iteration starts from an equivalent clean workspace, uses the
  same pinned execution configuration and deterministic acceptance contract,
  and retains raw per-invocation telemetry and environment evidence.
- Benchmark reports preserve raw successful and failed run results, summarize
  successful runs with median token, sequential-tool-batch, process, and timing
  metrics, and describe differences between modes as observed estimates rather
  than exact causal costs. Correctness and success rate remain visible alongside
  token cost.
- Release certification is tied to one clean, exact source revision. It rejects
  a dirty source tree before live model execution and requires deterministic
  checks plus installed-plugin evaluation for the same generated version.
- Release certification for a blocking local transport verifies that the
  supported host contains both the transport process and its descendants on
  normal interruption and hard host termination. A host without proven process
  tree cleanup is unsupported or produces an inconclusive certification rather
  than a successful release result.

## Durable Architecture And Constraints

- The production runtime targets .NET 10 and is packaged with the Factory
  plugin. A project-local runtime installation is not required.
- Factory CLI `run`, `continue`, and `cancel` remain complete production
  interfaces. Adapter transports invoke the runtime from their own installed
  plugin instance, return the existing structured CLI outcome, and do not add
  transport concepts to persisted Factory state.
- The effective workflow is a small, versioned, domain-specific YAML definition
  composed only from registered Factory primitives. A packaged default applies
  unless `.idd/factory.yaml` overrides supported composition and policies.
- Workflow validation rejects unsupported schemas, handlers, roles, transition
  targets, invalid limits, unreachable terminals, obvious unbounded cycles, and
  attempts to weaken non-negotiable safety invariants. The effective workflow
  hash is persisted and a change during a run is reported rather than silently
  adopted.
- Operational state is filesystem JSON in V1. SQLite, general scripting,
  arbitrary shell DSL, dynamic code loading, generic DAG primitives, and
  parallel implementation workers are outside this runtime.
- All semantic results use a versioned structured protocol written to an
  attempt-specific result artifact. Free-form stdout is not authoritative.
- Runtime-owned invocations distinguish logical role, logical skill identifier,
  execution profile, and dynamic input. Backend command syntax, skill discovery
  and activation, and sandbox or permission mapping remain adapter-owned.
- Legacy filename-status Factory state is detected and reported as unsupported;
  it is not reconstructed or migrated automatically. Existing historical
  result directories are not changed.
- Runtime, workflow schema, state schema, worker protocol, verification policy,
  and methodology versions are distinct compatibility dimensions.
- A missing project verification policy is a supported repository/platform
  fallback mode. Semantic workers use no invented stable check identifiers in
  that mode, while an existing policy remains authoritative and malformed
  existing policy is rejected rather than silently replaced by fallback.
- Backend-specific model flags, reasoning configuration, skill activation,
  plugin discovery, and capability isolation remain adapter or evaluation
  composition concerns; Factory Core does not encode Codex CLI syntax.
- Transport-specific discovery, direct-visibility configuration, timeout, and
  launcher syntax remain platform-adapter concerns. The Codex transport exposes
  only explicit Factory run, continue, and cancel operations and never invokes
  semantic workers directly.
- Project-local and domain skills may remain part of worker context. Whether
  user-global skills are inherited is an explicit capability policy and is
  fixed for release evaluation.
- Benchmark orchestration, workspace preparation, deterministic acceptance, and
  report generation are excluded from measured model token usage. Agent,
  acceptance, and end-to-end durations remain distinguishable.
- Ordinary deterministic repository checks build and test the benchmark runner
  without starting live Codex or Factory executions; live benchmarks require an
  explicit invocation.

## Non-goals

- A general-purpose agent orchestration, CI, distributed scheduling, or visual
  workflow platform.
- Parallel workers, worktrees, merge queues, or distributed leases in V1.
- Automatic product-intent editing by Factory workers.
- Persisting or replaying agent conversations as Factory memory.
- Requiring Claude support in V1.

## Acceptance Criteria

- A normal successful run performs decomposition, implementation, selective
  checkpoint review, final integrated review, and deterministic finalization
  without invoking `factory-step-coordinator` or `idd-factory-coordinate-step`.
- The default workflow and project override are validated before use, and the
  effective hash is stable and pinned to the run.
- Completed work and runner-owned state cannot be changed by a worker result.
- Failed verification never completes a work item and can deterministically
  invoke a bounded implementer verification-fix attempt and rerun the same gate.
  Repeated failure after the configured per-gate budget produces a structured
  blocked outcome without hidden retries or replanning.
- A green implementation path performs one implementer invocation and one
  authoritative runtime verification, with no verification-fix invocation.
- Checkpoint and final reviewers are never dispatched before their mandatory
  runtime verification gates pass.
- Checkpoint and final-review corrections create new work and repeat the
  corresponding review within budget.
- Restart and cancellation preserve enough evidence to avoid blind duplicate
  dispatch and to resume safely.
- Semantic clarification and blocked outcomes retain their exact worker reason
  and arbitrary structured payload across persisted state, CLI output, adapter
  transport, and answerless continuation without duplicate worker dispatch.
- Decomposition and replanning without `.idd/verification.yaml` proceed with no
  explicit stable check identifiers and leave authoritative fallback
  verification to the runtime; existing valid or invalid policy retains its
  strict runtime-owned semantics.
- State created through a CLI launcher can continue through an adapter
  transport, and state created through an adapter transport can continue
  through the CLI, without schema migration or changed workflow semantics.
- Final result artifacts, audit events, verification evidence, and semantic-role
  telemetry correspond to actual execution.
- Semantic-attempt telemetry identifies requested and effective execution
  configuration, selected Factory skill and source version, capability profile,
  skill inheritance counts, result-before-exit state, kill state, actual exit
  code when known, and termination kind. Missing effective backend evidence is
  reported as unknown and cannot silently satisfy a release assertion.
- Release evaluation proves that every semantic worker received the requested
  model and reasoning configuration and that all happy-path worker processes
  completed cleanly.
- Installation evaluation proves marketplace discovery, real plugin
  installation, packaged runtime completeness, installed plugin-root
  resolution, and supported refresh or reinstall behavior without simulating
  installation by copying Factory assets into the fixture workspace.
- Codex installation evaluation proves direct Factory-tool visibility without
  Code Mode or tool search, explicit-invocation-only behavior, one blocking
  launcher call, no launcher shell process or status polling, and no model
  iterations while the Factory call is active.
- A same-name non-Factory skill cannot be selected in place of the
  runtime-selected Factory skill. If the backend cannot guarantee identity, the
  attempt fails explicitly rather than dispatching ambiguously.
- Repeated release evaluation is independent of incidental user-global skills,
  while its capability profile and relevant skill counts remain observable.
- Evaluation reports show launcher, semantic-worker role and attempt breakdown,
  and end-to-end token totals separately; progress artifacts show only workflow
  state changes and survive successful Factory state cleanup.
- Benchmark modes can be selected independently and repeated without sharing a
  prior iteration's workspace. A failed iteration is recorded without stopping
  remaining work, and a requested mode with no successful iteration is reported
  distinctly from runner or configuration failure.
- Benchmark reports include the actual model, reasoning configuration, Codex,
  Factory and skill versions, source revision, benchmark definition identity,
  and relevant host environment. Reports expose comparability warnings when
  these defining conditions differ.
- Factory-decomposition replay retains the generated work-item contracts and
  their identities for inspection. When replay and the full Factory run cannot
  share one decomposition, the report records independent decomposition and
  accounts for its measured cost explicitly.
- Developer evaluation remains usable on dirty sources. Release certification
  rejects dirty sources early and records the full clean revision whose
  methodology, runtime, deterministic checks, installation test, and live run
  were certified.
- Core orchestration is testable without a real language model through fake
  backends, clocks, and process runners.

## Verification

Automated tests cover workflow safety, state revisions and immutability, agent
protocol validation, execution outcomes and retries, workspace fingerprints,
review corrections, replans, finalization, recovery, and cancellation. Live
Factory evaluations additionally verify the exact semantic role topology,
ordering, retry and correction counts, evidence, outcomes, and absence of
coordinator agents. Release checks also cover explicit worker execution
configuration, termination semantics, capability isolation and skill identity,
real installed-plugin lifecycle, token aggregation, progress projection, and
clean-revision certification. Public-directory runtime distribution remains a
separate evidence-gathering spike and is not assumed from repository
marketplace behavior.

Deterministic benchmark-runner tests cover declarative definitions and command
selection, median and overhead calculations, cached and new-input accounting,
multi-process aggregation, failed acceptance, sequential tool-batch detection,
and complete machine-readable and human-readable reporting using recorded
fixtures rather than live model execution. A small repository benchmark verifies
the shared-task, clean-workspace, deterministic-acceptance, and decomposition
capture contracts across all supported modes when invoked explicitly.
