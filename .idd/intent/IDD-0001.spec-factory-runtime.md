# IDD-0001.spec-factory-runtime

## Intent

IDD Factory executes a complete implementation request through a deterministic,
resumable .NET runtime. Semantic orchestration is a repeating bounded-batch
cycle:

```text
plan batch -> execute batch -> plan again
```

The planner is the only semantic component that decides what work remains and
which existing current durable-intent documents materially constrain each new
task. Each executor or research worker performs one immutable, self-contained
task and returns human-readable evidence of what happened. The runtime owns
state, ordering, recovery, retries, verification, budgets, persistence, stable
intent-ID resolution, and deterministic executor-context assembly.

For task-related durable intent the semantic/deterministic boundary is strict:
the planner selects relevant stable `IDD-NNNN` references per task; Factory
validates and persists those references, resolves them against current numbered
intent documents, and injects complete current document contents into executor
input. `TaskRelatedIntent` is task metadata binding durable truth to a work item,
not another source of truth.

When no further task can be safely contracted because a decision must come from
the user, planning may pause with one concrete question. The runtime owns only
the pause/resume mechanics. The user supplies the missing decision, and the
outer IDD workflow decides whether that answer changes durable intent before the
same Factory run resumes.

The authoritative execution model is immutable completed history, zero or one
current task, and one ordered current batch. Factory is not a task graph or a
general workflow engine.

## Request and Semantic Inputs

- The public Factory entry point accepts the complete user request and invokes a
  packaged Factory runtime for the selected workspace.
- Explicitly supplied pasted or attachment text is losslessly materialized
  before run creation. Host-local transport references are not durable request
  semantics. Invalid Unicode, replacement characters, or unresolved known
  attachment envelopes prevent creation rather than permitting corrupt state.
- The logical request is immutable and is supplied anew to every planning
  cycle. A planner evaluates current reality against that request rather than
  merely extending the previous local plan.
- Current durable intent is read-only Factory input and is refreshed for every
  planning cycle. Factory workers never mutate durable intent.
- On every planning cycle the planner reads `.idd/intent/README.md` and
  `.idd/intent/INDEX.md`, uses the index as the compact discovery catalog for
  plausible candidates, and reads only candidate current numbered documents
  whose contents are needed to determine task semantics or relevance. The index
  is not normative product content and the whole intent store is not loaded by
  default.
- Completed-task context contains the task contract, free-form semantic result,
  runtime-observed changed paths, and relevant authoritative verification
  evidence. Full worker transcripts and internal state dumps are not semantic
  inputs. Related-intent documents selected by completed tasks are not
  automatically propagated to later executors.
- Exact user answers to prior planning questions are stored as separate
  human-readable runtime artifacts and supplied to later planning cycles. They
  do not rewrite or append to the immutable original request.
- Semantic task contracts, results, questions, and user answers are stored as
  human-readable Markdown or text separately from machine-owned JSON metadata.
  Per-task durable-intent references are machine-owned work-item metadata and do
  not become part of `contract.md`.

## Bounded-Batch Planning

- Planning runs at the start of a run, after every current batch is exhausted,
  after strict final verification fails, and after a resumable planning question
  is answered.
- The planner inspects the original request, current durable intent, repository
  reality, completed results, authoritative verification evidence, and prior
  user answers recorded by the run.
- Each invocation materializes every task whose contract can be determined
  reliably now, in execution order, and stops at the first material uncertainty
  that depends on evidence from those tasks. A batch may contain multiple tasks
  and need not speculate through to final completion.
- For every new task the planner separately decides which current numbered
  durable-intent documents materially constrain correct implementation. It
  references those existing stable IDs in an optional `# TaskRelatedIntent`
  section after the concrete task contract. It does not include documents only
  because they belong to the product, are general subsystem background, may be
  useful, or are needed by another task.
- A task contract remains self-contained about the concrete result to produce.
  `TaskRelatedIntent` supplies additional normative durable constraints; it is
  not a substitute for the task contract. The planner does not copy, paraphrase,
  or summarize durable intent into a contract merely to avoid using the
  metadata.
- `# TaskRelatedIntent` belongs only to the immediately preceding `# Task`, may
  occur at most once for that task, terminates the contract body, and must be
  followed only by another `# Task` or end of output. It contains one or more
  canonical `IDD-NNNN` IDs, exactly one per non-empty line, in planner-selected
  order, with no bullets, filenames, paths, links, comments, prose,
  comma-separated lists, summaries, or duplicate IDs. Absence means an empty
  related-intent set.
- Planner output has exactly one logical form: an ordered set of non-empty
  `# Task` documents with optional per-task `# TaskRelatedIntent` metadata,
  exactly one non-empty `# Question` section, or exactly `# Done`. An exact
  `# Done` response means the planner's semantic reassessment found no remaining
  work and no missing user decision. Blank or whitespace-only planner output is
  malformed and is not a completion signal. The runtime does not require an
  approval, completion reason, confidence, outcome, capability selection,
  Factory/work-item identity, plan revision, or transition instruction from the
  planner. Referencing already-existing stable durable-intent IDs is semantic
  input selection, not runtime identity creation.
- When no task can be safely contracted now because a decision must come from
  the user, the planner may instead return exactly one non-empty `# Question`
  section. It must not mix `# Task`, `# Question`, and `# Done` in one response.
  Tasks that are already safely contractable execute in an earlier batch before
  a later planning cycle asks the question.
- The planner does not classify the question as `intent-required`, does not
  decide how the eventual answer should be stored in durable intent, and does
  not provide a runtime transition. It supplies only the semantic question.
- Runtime validates planner output mechanically. Before adopting a task batch it
  validates canonical related-intent ID syntax, duplicate absence, and that each
  reference resolves uniquely to exactly one direct current
  `.idd/intent/IDD-NNNN.*.md` document. Zero matches or multiple matches reject
  the entire planner batch through the planner/protocol failure path before any
  new contract is written or authoritative work-item identity is advanced.
- Runtime assigns monotonic work IDs, writes only the human-readable contracts,
  persists the ordered selected intent IDs as immutable work-item metadata, and
  atomically adopts the batch. For question output it creates a resumable
  `USER_DECISION_REQUIRED` blocker and exposes the question without creating a
  work item. For `# Done` it mechanically maps the validated marker to the
  existing empty-batch representation without adding semantic state.
- Runtime stable-ID resolution is deterministic and ordinal: it inspects only
  direct children of `.idd/intent/`, uses the exact canonical ID and filename
  shape `IDD-NNNN.*.md`, and does not use index prose, title, type, filename
  similarity, keyword matching, embeddings, path scoring, ranking, or document
  content to infer either identity or relevance.
- Invalid or partial planner output does not change the authoritative batch.
- Planner isolation permits reading the repository, intent, prior results,
  verification evidence, and prior user answers and writing only to its
  designated planning output. It cannot change product files or authoritative
  Factory state.
- New semantic work items originate only from planner output. There is no
  worker-driven prepend, correction batch, additional-work insertion, global
  replan request, checkpoint review dispatch, or final-review correction route.

## User-Decision Pause and Resume

- `USER_DECISION_REQUIRED` is available only at a planning boundary when the
  current batch is exhausted and no further task can be safely contracted.
- Runtime persists the planner question and stops without attempting to infer an
  answer, choose product semantics, edit intent, or create speculative work.
- An ordinary `continue` without an answer leaves the run paused.
- The host presents the question to the user. It must not fabricate an answer.
- After the user answers, the outer IDD workflow evaluates the answer together
  with the question and current relevant intent. Durable product or architecture
  truth is updated through the normal intent workflow when appropriate;
  implementation-only choices do not become durable intent merely because the
  planner asked about them.
- If intent changes, coverage is validated before Factory resumes.
- The exact user answer is then passed to `factory_continue`, persisted under the
  active run separately from `request.md`, and supplied to the next planner.
- If the user chooses not to continue, explicit cancellation preserves product
  changes and diagnostics.
- Executors cannot request this pause and their free-form reports are never
  parsed for user-question, intent, replan, correction, or completion signals.

## Batch Execution

- Runtime executes every task in the current batch sequentially in planner
  order. A task always observes the latest repository and relevant results from
  earlier tasks in the batch.
- Before every implementation executor invocation, Factory deterministically
  resolves that work item's persisted ordered `TaskRelatedIntentIds` and reads
  the complete current contents of each selected numbered document. The
  executor input places an explicit task-related durable-intent section between
  the task contract and completed-work context. An empty selection is rendered
  as `none`.
- Only documents explicitly selected for the current task are injected. Factory
  does not automatically inject `README.md`, `INDEX.md`, `GLOSSARY.md`, unrelated
  numbered documents, or documents referenced only by completed work.
- The selected ordered stable-ID sequence is immutable after materialization.
  Intent document contents are not snapshotted into `contract.md` or Factory
  state; the same IDs are resolved again on every invocation so their current
  document contents remain durable truth. If a previously valid persisted ID no
  longer resolves uniquely, Factory fails deterministically before executor
  dispatch rather than omitting, guessing, normalizing, or asking a worker to
  repair it.
- Executors treat both the concrete task contract and supplied task-related
  durable intent as normative inputs. Correctness for explicitly selected
  documents must not depend on repository rediscovery. Executors may still
  inspect repository code, additional durable intent, and the optional glossary
  when genuine implementation discovery makes that necessary; they are not
  instructed to scan the intent store routinely as a substitute for propagation.
- A worker cannot interrupt or mutate the batch based on a semantic judgment.
  Unexpected discoveries are recorded in its result for the next planner.
- Implementation executors may change product files and run focused development
  checks within their profile. Research remains an optional read-only execution
  capability when isolation is useful.
- Every executor and research worker answers only its assigned task and returns
  free-form human-readable text describing what was done, discovered, or left
  unresolved. No fixed report sections are required.
- Worker output contains no orchestration outcome or instruction such as
  additional work, correction, global replan, next task, future capability,
  approval, blocker routing, payload, or state transition. Runtime never parses
  the free-form semantic result to choose workflow.
- Runtime independently records actual changed paths, verification evidence,
  exit codes, attempt identity, timestamps, and state transitions.
- Shell commands started by a semantic worker are bounded. The runtime observes
  their lifecycle independently from the worker's prose: a command that remains
  active beyond the semantic-command timeout causes bounded termination of the
  complete worker process tree, and a worker result is rejected while any
  started command remains incomplete.
- A semantic worker may have multiple shell commands active concurrently.
  Factory tracks each command lifecycle independently. Command overlap itself is
  not a failure. Each command remains subject to its own semantic-command
  timeout, and a worker result is not trusted while any started command remains
  incomplete.
- A timed-out or abandoned worker command stops the current batch at the current
  work item. Factory preserves the command identity, bounded command text,
  elapsed time, available stdout and stderr, and termination outcome as local
  attempt evidence. It does not trust partial test results or dispatch later
  work from the batch on the basis of that attempt.

## Verification and Retry

- After a workspace-writing task, runtime selects authoritative focused
  verification from actual changed paths and project policy. Successful required
  verification is a precondition for moving the task to completed history.
- Unexpected focused-verification failure preserves the result, changed paths,
  and full failure evidence and retries the same immutable task within the
  ordinary per-task attempt budget. The next executor receives the relevant
  prior result and authoritative failure evidence. Planning is not invoked
  after an ordinary task-level verification failure.
- Every replacement executor invocation for the same work item preserves exactly
  the same ordered `TaskRelatedIntentIds`, whether it is a Semantic Retry, a
  Technical Restart, or a retry after semantic-budget extension. Each invocation
  resolves those same IDs against current durable intent and injects current
  complete document contents. Neither retry kind invokes the planner to
  reconsider semantic intent relevance.
- Runtime distinguishes **Semantic Retry** from **Technical Restart**
  deterministically. An unexpected authoritative task-verification failure occurs
  after a trusted semantic result and starts a new semantic implementation attempt,
  consuming the ordinary `maxAttemptsPerTask` budget. A restartable technical
  execution failure means no trusted semantic result was produced and starts a new
  executor invocation for the same semantic attempt instead.
- Restartable Technical Restart outcomes for implementation execution are
  `AGENT_COMMAND_TIMEOUT`, `AGENT_COMMAND_INCOMPLETE`, and
  `AGENT_TRANSPORT_FAILURE` only when no complete trusted result was observed.
  Arbitrary protocol exceptions are not restartable merely because they are
  protocol exceptions. Technical Restart never consumes the semantic attempt
  budget, remains available when that semantic budget is fully used, and consumes
  a separate cumulative `maxTechnicalRestartsPerTask` budget. Exhaustion is the
  terminal `TECHNICAL_RESTART_BUDGET_EXHAUSTED` blocker and cannot be extended by
  `factory_retry`.
- Expected intermediate failure, confirmation-required checks, and manual
  continuations remain explicit deterministic runtime mechanisms.
- When the planner explicitly returns `# Done`, runtime runs strict final
  deterministic verification. `# Done` itself never completes Factory. Final
  verification success permits finalization; failure becomes authoritative
  evidence for a new planning cycle and does not invoke a final semantic reviewer
  or a specialized correction protocol.
- Planning cycles, total work items, semantic attempts per task, and cumulative
  technical restarts per task are independently bounded and stop infinite execution
  with diagnostic state.
- Verification subprocess output is consumed incrementally and retained as
  separate stdout and stderr evidence. A timeout or bounded forced termination
  preserves all output already received and cannot create an unbounded cleanup
  wait.
- A verification infrastructure failure has one primary cause and stage.
  Termination, drain, cleanup, or diagnostic-write problems that occur while
  handling an earlier failure remain separate secondary diagnostic issues and
  never replace that primary cause. A normally completed process with a
  non-zero exit code remains an ordinary failed check.
- Verification infrastructure diagnostics are persisted locally as authoritative
  verification evidence. That evidence retains nullable exit status, timing,
  stdout/stderr metadata and bounded tails, workspace-relative full-log
  references, command metadata, exception details, termination outcome, and
  secondary diagnostic issues.
- The blocker and transport expose only the primary failure identity needed to
  report and resume the Factory operation: verification context, work item when
  applicable, check ID, failure kind, failure stage, and the persisted evidence
  reference when available. Detailed timing, process termination, stdout/stderr
  tails and log references, exception details, and secondary diagnostic issues
  are not duplicated into transport payloads.
- Run, continue, and status return the same persisted minimal blocker
  semantically. Baseline and ordinary verification use the same minimal failure
  reference while preserving their distinct continuation semantics.
- If evidence persistence fails, the evidence reference is null while the
  primary check, failure kind, and failure stage remain transport-visible. A
  later persistence failure is secondary to an already known primary
  infrastructure cause; otherwise it is the primary failure. State-store
  failures retain their existing independent semantics.

## State, Persistence, and Recovery

- Authoritative state is JSON under `.idd/factory/current/state.json` and uses a
  monotonic compare-and-swap revision in a single-run, single-writer model.
- State retains only what is necessary for the active run, current batch,
  current task, immutable completed work, planning cycles, separate semantic and
  technical execution counters, verification, continuations, recovery, budgets,
  final verification, and deterministic blockers. For a current work item it
  persists `SemanticAttemptCount`, cumulative `TechnicalRestartCount`,
  `AdditionalSemanticAttemptBudget`, and the exact `NextInvocationKind`.
- Each Remaining, Current, and Completed work item persists the exact ordered
  `TaskRelatedIntentIds` selected when that work item was materialized. The
  sequence is part of the immutable work-item definition and cannot change in
  content or order as the item moves Remaining -> Current -> retry -> Completed.
  Completion copies it exactly into immutable history.
- Later planning cycles may select different related intent for newly created
  work items. They never rewrite the selection of an existing or completed work
  item.
- State has no semantic-control fields or counters for replan triggers,
  post-completion routes, corrective cycles, last semantic outcomes,
  checkpoint review, or final semantic review.
- A pending user question is represented as a typed resumable continuation, not
  as an executor result or a future-work instruction.
- Exact question/answer text is preserved in human-readable runtime artifacts.
- Contracts are durable before referenced state, and state transitions are
  atomic. Orphan artifacts may remain diagnostic, but recovery follows
  authoritative state rather than replaying conversations.
- Semantic dispatch persists runtime-owned invocation identity before backend
  execution. Every executor invocation has a new unique `AttemptId` plus its work
  item, invocation kind, semantic-attempt number, and technical-restart number.
  Worker text cannot supply or alter runtime identity. Persisted results are bound
  to the exact invocation and consumed at most once.
- A restartable technical failure preserves runtime-observed workspace changes and
  bounded typed diagnostics but does not promote partial semantic output to a
  trusted prior result or send it to verification. Technical Restart runs against
  the current workspace; it is not an automatic rollback. The restart reason is
  persisted before the replacement invocation so process recovery resumes the
  same invocation kind without heuristic reconstruction.
- Recovery resumes the exact persisted planning, execution, verification,
  user-question, or continuation operation without asking an LLM to reconstruct
  orchestration or task-related intent references. Persisted planner output is
  reparsed under the current protocol: exact `# Done` remains valid, while blank
  output is malformed and is not grandfathered into semantic completion.
- This work-item invocation metadata changes active-state semantics. Runtime
  schema 14 does not implicitly migrate schema-13 active state or reinterpret its
  old `AttemptCount` as either semantic or technical history. Existing legacy
  cancellation/restart behavior remains the upgrade path.
- Deterministic runtime and environment failures—including sandbox, permission,
  missing executable, verification infrastructure, corrupted state, exhausted
  budget, cancellation, unavailable result channel, and a persisted related-
  intent ID that no longer resolves uniquely—remain typed blockers, not semantic
  worker reports.
- Explicit cancellation preserves product changes and diagnostics, including
  when the active state was written by an older runtime schema. A newer runtime
  can retire such a run without interpreting obsolete semantic outcomes, so the
  workspace can start a fresh run without reinstalling the older runtime.
- Continuation across a runtime-schema change is allowed only through an
  explicit, versioned migration whose source schema and invariants are known.
  When no such migration exists, `continue` reports that restart is required;
  it does not mutate, partially load, or relabel the legacy state.

## Finalization

- Finalization requires no active attempt, verification session, user question,
  or continuation; no current task or batch; and successful strict final
  verification for the current product snapshot.
- No mandatory final semantic review follows final verification. The repeated
  planner has already assessed integrated semantic reality, and deterministic
  verification supplies the terminal mechanical gate.
- Result artifacts are created and validated before current run state is
  cleared. Existing result directories are preserved with collision-safe
  suffixes.

## Configuration and Constraints

- The packaged default `factory.yaml` and optional workspace override configure
  bounded policy, registered execution capabilities, and verification behavior;
  they do not define workflow steps or a semantic state machine.
- Bounded policy exposes the semantic-command timeout explicitly. A workspace
  may lengthen or shorten it within the runtime safety ceiling; the effective
  value is recorded with every semantic attempt.
- Production runtime targets .NET 10 and is packaged with Factory plugins.
- Factory CLI and adapter transports preserve structured run, continue, cancel,
  blocker, and user-answer behavior without owning workflow semantics.
- Incomplete or blocked runs expose only the minimal primary verification
  failure reference through the existing payload. Detailed diagnostics remain
  available at the workspace-relative verification evidence path when it was
  successfully persisted. `ResultDirectory` remains reserved for successfully
  finalized results.
- The runtime does not use task graphs, dependency solvers, event sourcing,
  arbitrary scripting, dynamic code loading, parallel implementation workers,
  whole-workspace snapshots, automatic durable-intent editing, semantic intent
  relevance heuristics, or an additional semantic agent for intent selection.
- Semantic protocol and runtime schema may make a controlled versioned breaking
  change. Compatibility machinery must not preserve obsolete outcomes such as
  `additional-work-required`, `correction-required`, or
  `global-replan-required`.

## Acceptance Criteria

- Factory's normal workflow is planner determines remaining work, executor
  performs one task and reports what happened, and runtime executes the batch,
  verifies it, and plans again after exhaustion.
- Planner is the sole source of new semantic tasks and may create multiple
  reliably contractable tasks per invocation.
- The planner semantically selects stable durable-intent references independently
  for each new task; runtime never infers semantic relevance.
- Factory validates all selected IDs before batch adoption, persists the exact
  ordered selection as immutable work-item metadata, and injects complete
  current contents of exactly those selected documents into every executor
  invocation. Tasks with no selected intent remain valid and receive `none`.
- Executor correctness for explicitly selected intent does not depend on
  rediscovering the selected files. Unrelated intent, index content, and intent
  belonging only to completed tasks are not automatically injected.
- Retrying or recovering an existing work item preserves the same semantic
  selection without replanning while deterministically reloading current
  document contents. Completed work retains the same references for integrity
  and auditability.
- Factory runtime/work-item identity remains runtime-owned; planner references to
  existing `IDD-NNNN` durable-intent IDs do not create or choose runtime identity.
- Every exhausted batch causes a new planning cycle; planning stops at the first
  material uncertainty that needs evidence from the batch.
- If no further task can be contracted because a user decision is missing, the
  planner can return exactly one `# Question`; runtime pauses with
  `USER_DECISION_REQUIRED` and creates no work item from that question.
- A user answer resumes the same run, remains separate from immutable
  `request.md`, and is visible to later planners.
- The outer IDD workflow, not planner/runtime/executor, decides whether a user
  answer should update durable intent.
- Exact `# Done` planner output starts strict final verification without requiring
  a semantic approval or explanation; blank or whitespace-only output is rejected
  as `MALFORMED_PLANNER_OUTPUT`.
- Executor and research results are unrestricted human-readable text, are not
  parsed as workflow control, and need not list files, tests, concerns,
  decisions, findings, or blockers in fixed fields.
- Ordinary workers neither know nor select the next Factory step, future worker,
  capability, runtime ID, state transition, plan revision, or user-question
  continuation.
- Runtime executes all tasks in a batch in order even when an earlier result
  reports an unexpected discovery; the next planner evaluates the integrated
  state.
- Actual changed paths and all mechanical evidence are runtime-observed rather
  than declared by an LLM.
- Failed task verification retries the same task with authoritative evidence;
  failed final verification after `# Done` invokes the planner for a normal next
  batch.
- A semantic worker cannot complete successfully while one of its shell
  commands is still active. A command timeout or abandoned command terminates
  the worker process tree, preserves bounded diagnostic evidence and observed
  workspace effects, rejects any partial semantic result, and schedules a
  Technical Restart of the same semantic attempt before later batch work can run.
- Final deterministic verification remains runtime-owned and successful final
  verification can finalize without a semantic reviewer.
- Planner has write access only to designated planning output and cannot mutate
  product files or authoritative state.
- Runtime preserves crash recovery, single-writer atomic persistence, exact
  continuation, invocation/result binding, verification evidence, cancellation,
  safety budgets, and protected-artifact ownership.
- After an upgrade, a legacy active run can always be cancelled by the current
  runtime without losing product changes or its persisted diagnostics. A new run
  can then be started normally from a supplied request. No previous plugin
  version is required for this recovery path.
- An explicit restart validates the replacement request before retiring the
  active run, archives that run with the same preservation guarantees as
  cancellation, and starts the replacement under the current runtime while
  holding the workspace's single-writer ownership.
- Verification timeout, process-start, output-capture, and evidence-persistence
  failures expose only verification context, applicable work item, primary check,
  failure kind, failure stage, and nullable persisted evidence reference through
  blocker and transport payloads.
- Detailed timing, stdout/stderr metadata and bounded tails, full-log references,
  exception information, termination outcome, and secondary diagnostic issues
  remain correct in local verification evidence. Timeout cleanup, output capture,
  and full-log persistence guarantees are unchanged.
- Run, continue, and status replay the persisted minimal blocker semantically
  unchanged. Baseline and ordinary verification use the same minimal failure
  reference without merging terminal cancel/restart semantics with ordinary
  resumable `factory_continue` semantics.
- Verification-driven retry continues to receive bounded relevant failure output
  from authoritative evidence after stdout and stderr become separate evidence
  streams.
- Core deterministic tests and live evaluation cover multi-task batch planning,
  sequential execution, exhaustion-driven replanning, uncertainty-bounded
  follow-up batches, user-question pause/resume, explicit-`# Done` final
  verification, malformed blank planner output, final-failure replanning, local
  verification retry, recovery, isolation, and absence of worker-driven
  orchestration.

## Verification

Automated verification covers lossless request materialization, ordered batch
materialization and execution, immutable completed history, mechanical planner
output validation including exact `# Done` and task-related intent metadata,
free-form execution results, runtime-observed changes, protected artifact
ownership, deterministic durable-intent resolution, atomic rejection of invalid
related-intent batches, exact executor injection, same-task retry with preserved
intent IDs and prior failure evidence, planning after batch exhaustion, planning
question pause/resume with exact user answer transport, explicit-`# Done` final
verification, rejection of blank planner output, planning after strict final
failure, safety-budget exhaustion, exact-operation recovery, continuations,
cancellation, schema rejection, execution profiles, benchmark planner-output
compatibility, and collision-safe finalization.

Verification diagnostics are additionally covered for partial stdout and
stderr at timeout, output immediately preceding timeout, deterministic process
start and termination failures, bounded drain, individual log and evidence
persistence failures, local large-output evidence retention, ordinary non-zero
exits, minimal blocker/status replay, baseline continuation behavior, retry
evidence consumption, and supported reads of active legacy evidence where
runtime upgrade policy permits continuation.

Semantic-worker execution is additionally covered for concurrent shell commands,
a shell command that exceeds its timeout, a worker that exits after abandoning
a started command, result observation while commands remain active, buffered
command completion during process-output drain, bounded process-tree
termination, rejection of partial results, preservation of command diagnostics,
same-task retry with that evidence, and prevention of later batch dispatch until
the current task is resolved.

## Non-goals

- A task graph, dependency solver, topology mutation framework, or speculative
  full-project roadmap.
- Worker-driven creation, insertion, replacement, or categorization of future
  work.
- Executor-driven user questions, intent outcomes, or replanning signals.
- Semantic checkpoint or final reviewers in the normal workflow.
- A universal structured semantic result shared by planning, execution, and
  research.
- Compatibility adapters that perpetuate the previous semantic outcome
  protocol.
- A general-purpose workflow engine, CI system, distributed scheduler, or
  parallel implementation platform.
