# IDD-0001.spec-factory-runtime

## Intent

IDD Factory executes a complete implementation request through a deterministic,
resumable .NET runtime. Semantic orchestration is a repeating bounded-batch
cycle:

```text
plan batch -> execute batch -> plan again
```

The planner is the only semantic component that decides what work remains.
Each executor or research worker performs one immutable, self-contained task
and returns human-readable evidence of what happened. The runtime owns state,
ordering, recovery, retries, verification, budgets, persistence, and all
transitions between planning and execution.

The authoritative execution model is immutable completed history, zero or one
current task, and one ordered current batch. Factory is not a task graph or a
general workflow engine.

## Request and Semantic Inputs

- The public Factory entry point accepts the complete user request and invokes a
  packaged Factory runtime for the selected workspace.
- Explicitly supplied pasted or attachment text is losslessly materialized
  before run creation. Host-local transport references are not durable request
  semantics. Invalid Unicode, replacement characters, or unresolved known
  attachment envelopes prevent creation rather than permitting corrupt state.
- The logical request is immutable and is supplied anew to every planning
  cycle. A planner evaluates current reality against that request rather than
  merely extending the previous local plan.
- Current durable intent is read-only Factory input and is refreshed for every
  planning cycle. Factory workers never mutate durable intent.
- Completed-task context contains the task contract, free-form semantic result,
  runtime-observed changed paths, and relevant authoritative verification
  evidence. Full worker transcripts and internal state dumps are not semantic
  inputs.
- Semantic task contracts and results are stored as human-readable Markdown or
  text separately from machine-owned JSON metadata.

## Bounded-Batch Planning

- Planning runs at the start of a run, after every current batch is exhausted,
  after strict final verification fails, and after a resumable intent stop is
  resolved.
- The planner inspects the original request, current durable intent, repository
  reality, completed results, authoritative verification evidence, and any
  unexecuted current plan needed for context.
- Each invocation materializes every task whose contract can be determined
  reliably now, in execution order, and stops at the first material uncertainty
  that depends on evidence from those tasks. A batch may contain multiple tasks
  and need not speculate through to final completion.
- Planner output is only an ordered set of non-empty task documents. Empty
  output means no remaining semantic work. The runtime does not require an
  approval, completion reason, confidence, outcome, capability selection,
  persistent identity, plan revision, or transition instruction from the
  planner.
- Runtime validates planner output mechanically, assigns monotonic work IDs and
  runtime metadata, writes immutable contracts, and atomically adopts the
  batch. Invalid or partial planner output does not change the authoritative
  batch.
- Planner isolation permits reading the repository, intent, prior results, and
  verification evidence and writing only to its designated planning output.
  It cannot change product files or authoritative Factory state.
- New semantic work items originate only from planner output. There is no
  worker-driven prepend, correction batch, additional-work insertion, global
  replan request, checkpoint review dispatch, or final-review correction route.

## Batch Execution

- Runtime executes every task in the current batch sequentially in planner
  order. A task always observes the latest repository and relevant results from
  earlier tasks in the batch.
- A worker cannot interrupt or mutate the batch based on a semantic judgment.
  Unexpected discoveries are recorded in its result for the next planner.
- Implementation executors may change product files and run focused development
  checks within their profile. Research remains an optional read-only execution
  capability when isolation is useful.
- Every executor and research worker answers only its assigned task and returns
  free-form human-readable text describing what was done, discovered, or left
  unresolved. No fixed report sections are required.
- Worker output contains no orchestration outcome or instruction such as
  additional work, correction, global replan, next task, future capability,
  approval, blocker routing, payload, or state transition. Runtime never parses
  the free-form semantic result to choose workflow.
- Runtime independently records actual changed paths, verification evidence,
  exit codes, attempt identity, timestamps, and state transitions.

## Verification and Retry

- After a workspace-writing task, runtime selects authoritative focused
  verification from actual changed paths and project policy. Successful required
  verification is a precondition for moving the task to completed history.
- Unexpected focused-verification failure preserves the result, changed paths,
  and full failure evidence and retries the same immutable task within the
  ordinary per-task attempt budget. The next executor receives the relevant
  prior result and authoritative failure evidence. Planning is not invoked
  after an ordinary task-level verification failure.
- Expected intermediate failure, confirmation-required checks, and manual
  continuations remain explicit deterministic runtime mechanisms.
- When the planner returns no tasks, runtime runs strict final deterministic
  verification. Success permits finalization. Failure becomes authoritative
  evidence for a new planning cycle; it does not invoke a final semantic
  reviewer or a specialized correction protocol.
- A planner may produce an empty batch repeatedly only as allowed by bounded
  runtime policy. Budgets such as maximum planning cycles, total work items, and
  attempts per task stop infinite execution with diagnostic state.

## State, Persistence, and Recovery

- Authoritative state is JSON under `.idd/factory/current/state.json` and uses a
  monotonic compare-and-swap revision in a single-run, single-writer model.
- State retains only what is necessary for the active run, current batch,
  current task, immutable completed work, planning cycles, attempts,
  verification, continuations, recovery, budgets, final verification, and
  deterministic blockers.
- State has no semantic-control fields or counters for replan triggers,
  post-completion routes, corrective cycles, last semantic outcomes,
  checkpoint review, or final semantic review.
- Contracts are durable before referenced state, and state transitions are
  atomic. Orphan artifacts may remain diagnostic, but recovery follows
  authoritative state rather than replaying conversations.
- Semantic dispatch persists runtime-owned invocation identity before backend
  execution. Worker text cannot supply or alter runtime identity. Persisted
  results are bound to the exact invocation and consumed at most once.
- Recovery resumes the exact persisted planning, execution, verification, or
  continuation operation without asking an LLM to reconstruct orchestration.
- Deterministic runtime and environment failures—including sandbox, permission,
  missing executable, verification infrastructure, corrupted state, exhausted
  budget, cancellation, and unavailable result channel—remain typed blockers,
  not semantic worker reports.
- Explicit cancellation preserves product changes and diagnostics. Incompatible
  active legacy state is rejected explicitly; the new semantic protocol carries
  no compatibility layer for old worker outcomes.

## Finalization

- Finalization requires no active attempt, verification session, or
  continuation; no current task or batch; and successful strict final
  verification for the current product snapshot.
- No mandatory final semantic review follows final verification. The repeated
  planner has already assessed integrated semantic reality, and deterministic
  verification supplies the terminal mechanical gate.
- Result artifacts are created and validated before current run state is
  cleared. Existing result directories are preserved with collision-safe
  suffixes.

## Configuration and Constraints

- The packaged default `factory.yaml` and optional workspace override configure
  bounded policy, registered execution capabilities, and verification behavior;
  they do not define workflow steps or a semantic state machine.
- Production runtime targets .NET 10 and is packaged with Factory plugins.
  Factory CLI and adapter transports preserve the same structured run,
  continue, cancel, and blocker outcomes without owning workflow semantics.
- The runtime does not use task graphs, dependency solvers, event sourcing,
  arbitrary scripting, dynamic code loading, parallel implementation workers,
  whole-workspace snapshots, or automatic durable-intent editing.
- Semantic protocol and runtime schema may make a controlled versioned breaking
  change. Compatibility machinery must not preserve obsolete outcomes such as
  `additional-work-required`, `correction-required`, or
  `global-replan-required`.

## Acceptance Criteria

- Factory's normal workflow is fully described as planner determines remaining
  work, executor performs one task and reports what happened, and runtime
  executes the batch, verifies it, and plans again after exhaustion.
- Planner is the sole source of new semantic tasks and may create multiple
  reliably contractable tasks per invocation.
- Every exhausted batch causes a new planning cycle; planning stops at the first
  material uncertainty that needs evidence from the batch.
- Empty planner output starts strict final verification without requiring a
  semantic approval or explanation.
- Executor and research results are unrestricted human-readable text, are not
  parsed as workflow control, and need not list files, tests, concerns,
  decisions, findings, or blockers in fixed fields.
- Ordinary workers neither know nor select the next Factory step, future worker,
  capability, runtime ID, state transition, or plan revision.
- The normal semantic protocol contains no additional-work, correction, global
  replan, checkpoint-review, or final-review outcomes and no universal semantic
  result DTO or outcome-specific contract matrix.
- Runtime executes all tasks in a batch in order even when an earlier result
  reports an unexpected discovery; the next planner evaluates the integrated
  state.
- Actual changed paths and all mechanical evidence are runtime-observed rather
  than declared by an LLM.
- Failed task verification retries the same task with authoritative evidence;
  failed final verification invokes the planner for a normal next batch.
- Final deterministic verification remains runtime-owned and successful final
  verification can finalize without a semantic reviewer.
- Planner has write access only to designated planning output and cannot mutate
  product files or authoritative state.
- Runtime preserves crash recovery, single-writer atomic persistence, exact
  continuation, invocation/result binding, verification evidence, cancellation,
  safety budgets, and protected-artifact ownership.
- Core deterministic tests and live evaluation cover multi-task batch planning,
  sequential execution, exhaustion-driven replanning, uncertainty-bounded
  follow-up batches, empty-plan final verification, final-failure replanning,
  local verification retry, recovery, isolation, and absence of worker-driven
  orchestration.

## Verification

Automated verification covers lossless request materialization, ordered batch
materialization and execution, immutable completed history, mechanical planner
output validation, free-form execution results, runtime-observed changes,
protected artifact ownership, same-task retry with prior failure evidence,
planning after batch exhaustion, empty-plan final verification, planning after
strict final failure, safety-budget exhaustion, exact-operation recovery,
continuations, cancellation, schema rejection, execution profiles, and
collision-safe finalization.

Live evaluation additionally proves real multi-task planning, sequential
execution, planner isolation, research and implementation result handling,
installed-plugin lifecycle, token aggregation, and the absence of semantic
coordinator, checkpoint-review, final-review, and worker-controlled future-work
paths.

## Non-goals

- A task graph, dependency solver, topology mutation framework, or speculative
  full-project roadmap.
- Worker-driven creation, insertion, replacement, or categorization of future
  work.
- Semantic checkpoint or final reviewers in the normal workflow.
- A universal structured semantic result shared by planning, execution, and
  research.
- Compatibility adapters that perpetuate the previous semantic outcome
  protocol.
- A general-purpose workflow engine, CI system, distributed scheduler, or
  parallel implementation platform.
