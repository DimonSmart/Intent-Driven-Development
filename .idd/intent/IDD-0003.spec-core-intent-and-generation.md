# IDD-0003.spec-core-intent-and-generation

## Intent

IDD keeps durable product memory compact and current while implementation workflow remains disposable. `idd-intent` is the standalone core plugin; `idd-factory` is optional and depends on it. Factory orchestration behavior is owned by IDD-0001 and its architecture by IDD-0006.

## Product model

`.idd/intent/` contains current specs, ADRs, and active spikes; Git stores history. Tasks, progress, plans, review notes, and generated reports are not intent. `GLOSSARY.md` is optional and contains only terms whose ambiguous interpretation could materially change understanding; it is not a general dictionary.

Projects may optionally keep `.idd/engineering/` for project-owned durable implementation guardrails. It is separate from product intent, Factory state, and `.idd/verification.yaml`. Its absence is valid. Engineering Rules use stable `ENG-NNNN` IDs, support only `Always` and `Conditional` applicability, have no archive lifecycle, and are never inferred or migrated automatically from current implementation or existing Intent.

`idd-engineering-change`, owned by the `idd-intent` plugin, is the standard workflow for explicit project-owned Engineering Rule add, modify, and remove mutations. It acts only on explicit durable engineering decisions, never promotes a current code pattern by itself, and blocks mutation while `.idd/factory/current/request.md` marks an active Factory run. A single request may contain multiple durable decisions: the workflow completes semantic grouping, ownership resolution, ambiguity detection, and ID-capacity planning for the whole batch before mutation. The Engineering layer is created lazily only when that plan requires a real add, using canonical bootstrap assets; `idd-project-init` does not create it. Once allocator metadata exists, `INDEX.md` owns an authoritative `Next ID: ENG-NNNN`; only new Rules consume sequential IDs, while modifications, no-ops, and removals do not consume IDs. A valid legacy Engineering layer without allocator metadata remains readable and gains `Next ID = max(current ENG IDs) + 1` only immediately before its first real management mutation. Engineering structural validation is performed directly from the shared canonical Mechanical Engineering Validation checklist rather than by invoking another skill. Routing classifies these requests as `engineering-change`, and other IDD skills may read, validate, report candidates, or hand off to `idd-engineering-change` but do not independently mutate Engineering Rules.

`src/canonical/` is the source of truth for distributable IDD content. `plugin-manifest.json` defines logical plugins, dependencies, skills, references, assets, and plugin metadata. `skill-descriptions.json` defines skill descriptions, manual/automatic invocation policy, and adapter-specific front matter; for Claude this includes details such as context, agent, argument hints, and `allowed-tools`. `src/adapters/claude/adapter.json` and `src/adapters/codex/adapter.json` describe host entry points and adapter capabilities.

The generator validates these inputs and produces Claude and Codex marketplace/plugin artifacts from the same canonical skill bodies. The core plugin packages canonical optional Engineering bootstrap definitions without causing `idd-project-init` to create `.idd/engineering/` by default. Factory plugins contain skills, references, adapter metadata, and bootstrap assets only; they do not package a Factory runtime or MCP transport. Platform adapters may change packaging, front matter, native-agent guidance, and host-specific metadata, but not canonical meaning. Generated output is derivative and must not be maintained as a separate source. Generated plugin metadata records the platform/version and points back to `src/canonical` as the canonical source.

Factory work items and active state are temporary, Git-ignored operational artifacts. Successful finalization clears active state; retained diagnostics do not become intent automatically. Shared task context may be stored once and referenced by small work items to avoid repeating common instructions.

Task-related propagation does not create another durable-knowledge layer. A Factory task may persist planner-selected stable `IDD-NNNN` references in `TaskRelatedIntent` and planner-selected Conditional `ENG-NNNN` references in `TaskRelatedEngineering`. Those references point to existing current documents and do not copy or derive another source of truth. Always Engineering Rules are not planner output; the orchestrator mechanically enumerates the current Always set before each worker execution. The worker resolves all supplied IDs and reads the current documents itself as defined by IDD-0001.

## Self-hosting

This repository defines IDD and uses IDD to describe itself. `.idd/intent/` states product intent; the repository does not create `.idd/engineering/` merely to demonstrate the optional feature; `src/canonical/` implements the distributable method; adapter/generator code implements native packaging; generated plugins are output only. For changes to IDD itself, update the smallest owning intent document when durable behavior changes, then update implementation. Do not recursively bootstrap IDD from its own generated plugins or regenerate self-intent from implementation.

When Factory runs on this repository, `TaskRelatedIntentIds` may therefore reference the same `.idd/intent/` documents that define Factory and IDD. This is ordinary self-hosting: the work item points to existing product intent so an executor receives the relevant durable constraints. It must not be interpreted as intent containing or generating another intent, nor as permission for Factory workers to edit durable intent.
