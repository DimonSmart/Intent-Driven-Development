# IDD-0003.spec-core-intent-and-generation

## Intent

IDD keeps durable product memory compact and current while implementation workflow remains disposable. `idd-intent` is the standalone core plugin; `idd-factory` is optional and depends on it. Factory orchestration behavior is owned by IDD-0001 and its architecture by IDD-0006.

## Product model

Confirmed visual appearance, hierarchy, density, color/shape identity and
other product-significant perceptual relationships can be durable Product
Intent even without a functional behavior change. The existing
`idd-intent-visual-brainstorm` provides read-only discovery from references;
its observations, guesses and comparison-card choices are not automatically
normative. After approval and a separate persistence request,
`idd-intent-change` records confirmed meaning, applicability, obligation
strength and permitted freedom in the current owning spec under
`.idd/intent/`. An already approved handoff needs no repeat brainstorm.
Unconfirmed image details or missing essential scope must not become product
truth. Exact fidelity to an image needs an accessible stable reference for
parts that cannot independently be expressed and verified in words.

The same ordinary `add`, `modify`, `remove` and `not-applicable` outcomes
cover behavior and visual product requirements. Visual `Essential` properties
are binding within their confirmed scope; `Preferred` properties admit
justified alternatives, `Free` marks implementation freedom, and `Avoid`
retains the agreed strength of prohibition. A current spec must communicate
these distinctions, exceptions and meaningful acceptance/verification to a
fresh Coding Agent with no chat or gallery. Later modifications and removals
replace obsolete visual requirements and reconcile associated verification
without erasing unrelated behavior, UX, accessibility or compatibility.
Ownership is by product area, not a separate visual directory or mandatory
`## Visual Intent` section; create a new owning spec only if no existing
spec owns the requirement. A purely local appearance implementation within
current Intent remains implementation-only. No mandatory designer workflow,
reference store, Factory phase or visual test engine is introduced.

`.idd/intent/` contains current specs, ADRs, and active spikes; Git stores history. Tasks, progress, plans, review notes, and generated reports are not intent. `GLOSSARY.md` is optional and contains only terms whose ambiguous interpretation could materially change understanding; it is not a general dictionary.

Project initialization is state-minimal: `idd-project-init` materializes only the
`.idd/intent/` bootstrap state plus the active Coding Agent instruction block. It
does not create or maintain a project-level plugin manifest or any replacement
feature manifest. The instruction block links to official IDD plugin installation
instructions; plugins themselves remain Coding Agent environment state. Factory-specific
initialization behavior is selected only by an explicit Factory request or by
existing Factory-specific project state such as `.idd/execution.yaml` or
`.idd/factory/`; the fact that `idd-factory` is installed in the Coding Agent
is never project-state evidence.

Projects may optionally keep `.idd/engineering/` for project-owned durable implementation guardrails. It is separate from product intent, Factory state, `.idd/verification.yaml`, and the optional `.idd/execution.yaml` Factory execution policy. Its absence is valid. Engineering Rules use stable `ENG-NNNN` IDs, support only `Always` and `Conditional` applicability, have no archive lifecycle, and are never inferred or migrated automatically from current implementation or existing Intent.

`idd-engineering-change`, owned by the `idd-intent` plugin, is the standard workflow for explicit project-owned Engineering Rule add, modify, and remove mutations. It acts only on explicit durable engineering decisions, never promotes a current code pattern by itself, and blocks mutation while `.idd/factory/current/request.md` marks an active Factory run. A single request may contain multiple durable decisions: the workflow completes semantic grouping, ownership resolution, ambiguity detection, and ID-capacity planning for the whole batch before mutation. The Engineering layer is created lazily only when that plan requires a real add, using canonical bootstrap assets; `idd-project-init` does not create it. Once allocator metadata exists, `INDEX.md` owns an authoritative `Next ID: ENG-NNNN`; only new Rules consume sequential IDs, while modifications, no-ops, and removals do not consume IDs. A valid legacy Engineering layer without allocator metadata remains readable and gains `Next ID = max(current ENG IDs) + 1` only immediately before its first real management mutation. Engineering structural validation is performed directly from the shared canonical Mechanical Engineering Validation checklist rather than by invoking another skill. Routing classifies ordinary Engineering management requests as
`engineering-change`. `idd-intent-import` is the bounded exception for
migration of explicit durable Engineering knowledge already present in supplied
import sources: it may create or update Rules without repeated confirmation, but
may not infer policy from implementation reality, choose among alternatives,
perform ordinary Rule removal, or modify `.idd/verification.yaml`. Other IDD
skills may read, validate, report candidates, or hand off to
`idd-engineering-change` but do not independently mutate Engineering Rules.

IDD exposes three distinct public Intent inspection mechanisms:

```text
idd-intent-lint
    mechanical consistency of .idd/intent/, read-only by default; with
    explicit fix authorization conservatively repairs unique technical
    defects (filenames/H1/INDEX/local links/managed headings and missing
    canonical bootstrap) and revalidates the result

idd-intent-structure-audit
    semantic structure and organization of current Product Intent

idd-intent-drift-audit
    conformance of current implementation to current Product Intent
```

`idd-intent-lint` defaults to `check`, never changing project files. Its
explicit `fix` mode changes only unambiguous mechanical Intent details:
stable IDs do not change, user requirements, comments and custom INDEX
metadata remain intact, and conflicting identities are reported rather than
guessed. Missing standard files in an already initialized Intent directory
are restored solely from lint's packaged canonical bootstrap assets.
`GLOSSARY.md` and optional Engineering Rules, including allocator state,
are read-only for both modes. Lint is not semantic normalization, does not
run a global Markdown formatter, and performs no automatic Git commits or
rollback. Claude and Codex share canonical checks and safety guarantees.
Claude lint may use a general-purpose forked agent to perform explicitly
authorized writes while the default check remains behaviorally read-only.

`idd-intent-drift-audit` is read-only and always has an explicit scope.
Focused and explicitly project-wide scopes are both valid. A project-wide audit
is Intent-driven: it discovers current Intent ownership first, then maps durable
behavior to implementation and verification evidence. It is not a generic code
review. Durable observable implementation behavior without a current Product
Intent owner may be reported as missing intent; private implementation details
are not Product Intent merely because they exist.

Technical implementation verification remains operational policy in
`.idd/verification.yaml`. Implementation and Factory workflows resolve and run
permitted checks; drift audit interprets that evidence relative to Product
Intent. No separate generic public verification skill is part of the model.

`src/canonical/` is the source of truth for distributable IDD content. `plugin-manifest.json` defines logical plugins, dependencies, skills, references, assets, and plugin metadata. `skill-descriptions.json` defines skill descriptions, manual/automatic invocation policy, and adapter-specific front matter; for Claude this includes details such as context, agent, argument hints, and `allowed-tools`. `src/adapters/claude/adapter.json` and `src/adapters/codex/adapter.json` describe host entry points and adapter capabilities.

The generator validates these inputs and produces Claude and Codex marketplace/plugin artifacts from the same canonical skill bodies. The core plugin packages canonical optional Engineering bootstrap definitions without causing `idd-project-init` to create `.idd/engineering/` by default. Factory plugins contain skills, references, adapter metadata, and bootstrap assets only; they do not package a Factory runtime or MCP transport. Platform adapters may change packaging, front matter, native-agent guidance, and host-specific metadata, but not canonical meaning. Generated output is derivative and must not be maintained as a separate source. Generated plugin metadata records the platform/version and points back to `src/canonical` as the canonical source.

Factory work items and active state are temporary, Git-ignored operational artifacts. Successful finalization clears active state; retained diagnostics do not become intent automatically. In contrast, `.idd/execution.yaml` is project-owned persistent operational policy for native child model overrides; it survives runs and remains outside `.idd/factory/current/`. Shared task context may be stored once and referenced by small work items to avoid repeating common instructions.

Task-related propagation does not create another durable-knowledge layer. A Factory task may persist planner-selected stable `IDD-NNNN` references in `TaskRelatedIntent` and planner-selected Conditional `ENG-NNNN` references in `TaskRelatedEngineering`. Those references point to existing current documents and do not copy or derive another source of truth. Always Engineering Rules are not planner output; the orchestrator mechanically enumerates the current Always set before each worker execution. The worker resolves all supplied IDs and reads the current documents itself as defined by IDD-0001.

## Business Complexity Assessment

The core `idd-intent` plugin provides `idd-intent-estimate` as an explicitly
invocable and automatically selectable read-only skill for qualitative analysis
of current Product Intent. It works before implementation exists and never
reads implementation to determine product difficulty, modifies Intent, or
starts Factory. Users may assess the full accessible current Intent or a named
functional area; the report states the boundary, actual current document
evidence and gaps.

The business assessment separates functional Product Scope, qualitative
Implementation Complexity and Assessment Confidence. It assesses seven distinct
qualitative dimensions: Functional Scope, Business Logic, Integrations,
Data Complexity, Reliability & Security, User Interaction, and Operational
Constraints. Unknown requirements cannot be scored Low by omission. Temporary
analysis is returned as Markdown and is not stored as normative Intent.
COSMIC Preparation may extract candidate processes, users and possible data
movements only where the scope/boundary and sources justify them; it does not
calculate CFP, effort, budget, timelines or implementation progress.
Confirmed inter-process connector fan-in may contribute to qualitative
integration/change-impact judgment with a traced causal explanation, but does
not create duplicate process scope or automatically imply a High rating.

## COSMIC Functional Size Measurement

The independent, target-project-read-only `idd-intent-cosmic` skill measures
COSMIC v5.0 size from current numbered Product Intent, not implementation.
It never converts CFP to effort, duration, price, or general algorithmic difficulty.
All accessible current normative specs in the requested scope must be reviewed
in full before a complete documented-scope measurement can be returned.

**Single normative process ownership is assumed.** Each functional process
is defined by one owning current specification (which may contain several
processes); another specification can refer to it through a directed connector
without redefining its requirements, creating a new functional process or
contributing extra COSMIC movements. True duplicate normative process
definitions are a structure-audit/lint issue, not a semantic deduplication
operation during measurement. An unresolved reference does not create a
process automatically.

Every substantive spec is inspected by a fresh, isolated reader agent.
Large documents can be divided into source-proven ranges and consolidated
without inventing processes per section. Compact owner/process and
connector indexes are merged through fresh bounded agents, with cross-group
reference targets verified. Separate fresh process-measurer agents examine
the exact source-backed E/X/R/W of each owned process or bounded group.
The final aggregator uses compatible confirmed owner-process measurements
only. No single LLM context must hold all raw specs or all measurements.

The report includes a **non-COSMIC Coupling / Change Impact** view:
confirmed distinct incoming caller processes, separately labeled referring
specifications, outbound links and source-supported qualitative integration/
change risks. More consumers can raise the *qualitative* impact of changing a
process; coupling does not multiply CFP and is not a person-hours estimate.

Coverage and lossless evidence extraction are tracked through simple,
persistent, user-visible Markdown packets in a cache folder **outside** the
target repository: one `IDD-NNNN.cosmic.md` file per numbered current Intent
source. Each completed packet records the same source ID, exact source path,
complete read-range evidence, canonical owner-process facts, LINK connectors,
movement candidates and uncertainties, with an explicit completion marker.
For a new request, an existing matching completed packet is reused without
rereading its source; only missing, incomplete or explicitly refreshed sources
require isolated Readers. A user can select specific IDD IDs for a new
measurement or request a refresh/clear of selected or all cache entries.

Reader packets preserve **extraction**, not COSMIC CFP verdicts. Every measurement
recalculates selected owner-process CFP under the current boundary using fresh
bounded measurers; links remain separate from CFP. Scoped results must not
pretend to cover unrelated documents or full-project coupling.

There are **no hashes, timestamps, automatic invalidation, generated JSON state,
additional helper scripts or mandatory execution runtime**. The source inventory
and completed packet filenames are the work queue and resume mechanism.
Cached reader packets are accepted as user-controlled source snapshots, and
reports explicitly disclose `Cached input — source freshness not verified`
when previously extracted packets were reused. The user requests refresh
when the Product Intent has changed; stale packets are not silently certified.
Writes/deletions are limited to the external cache directory through native
host file operations, never normative Product Intent. Completed evidence must
survive context compression and can be inspected by ID. Invalid or truncated
outputs cannot be accepted as completed packets; retries are bounded.

Failures of agent isolation, incomplete packets and unrecoverable context or
state limitations are technical `Execution incomplete / BLOCKED` outcomes,
not unspecified product requirements. Genuine ambiguous documented FUR can
lead to justified Analytical Partial; incomplete reading can never be
presented as a completed whole-product measurement. User-facing Markdown
contains detailed evidence and coverage, while compact coordinator packets
remain internal and separate.

## Self-hosting

This repository defines IDD and uses IDD to describe itself. `.idd/intent/` states product intent; the repository does not create `.idd/engineering/` merely to demonstrate the optional feature; `src/canonical/` implements the distributable method; adapter/generator code implements native packaging; generated plugins are output only. For changes to IDD itself, update the smallest owning intent document when durable behavior changes, then update implementation. Do not recursively bootstrap IDD from its own generated plugins or regenerate self-intent from implementation.

When Factory runs on this repository, `TaskRelatedIntentIds` may therefore reference the same `.idd/intent/` documents that define Factory and IDD. This is ordinary self-hosting: the work item points to existing product intent so an executor receives the relevant durable constraints. It must not be interpreted as intent containing or generating another intent, nor as permission for Factory workers to edit durable intent.
