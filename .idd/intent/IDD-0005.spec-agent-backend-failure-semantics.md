# IDD-0005.spec-agent-backend-failure-semantics

## Intent

Factory distinguishes failures of the external Agent Backend from semantic failure of the requested work and from restartable process/transport instability. Backend availability is runtime-owned technical state and must never be reinterpreted by the planner or another LLM.

## Runtime semantics

Three deterministic backend conditions are resumable external blockers:

- `AGENT_CAPACITY_UNAVAILABLE` for explicit usage/quota/account/model limits;
- `AGENT_RATE_LIMITED` for explicit backend rate limiting;
- `AGENT_AUTHENTICATION_REQUIRED` for explicit missing, invalid, or expired authentication.

Known external blockers pause the exact pending semantic operation. They do not schedule Semantic Retry or Technical Restart, do not consume `maxAttemptsPerTask`, do not consume `maxTechnicalRestartsPerTask`, and do not consume a planning cycle. `factory_continue` creates a new physical `AttemptId` and replays the persisted `OperationInput` for the same logical operation. For execution the same immutable work item, `TaskRelatedIntentIds`, `RelevantCompletedWorkIds`, semantic-attempt number, and technical-restart number are preserved.

A failed physical invocation remains immutable history. Any partial workspace changes discovered for it are retained under the normal changed-path rules and the replacement invocation runs against the actual current workspace.

## Classification boundary

Backend failure classification is deterministic and belongs next to Agent Backend execution. Structured backend error events have priority, followed by bounded backend `stderr`, then bounded `stdout` only for a failed backend invocation. Matching is conservative and backend-specific where needed; arbitrary words such as `limit`, `quota`, `auth`, or `429` in ordinary agent output are not sufficient. No LLM participates in classification.

A complete trusted semantic result keeps existing success semantics even if trailing diagnostics resemble a backend blocker. Cancellation keeps cancellation semantics. `AGENT_COMMAND_TIMEOUT` and `AGENT_COMMAND_INCOMPLETE` keep their existing Technical Restart semantics. Unknown failed transport/process outcomes fall back to `AGENT_TRANSPORT_FAILURE`.

## Diagnostics and recovery

Every classified failed Agent invocation has a bounded normalized `attempts/<AttemptId>/failure-diagnostic.json` containing the failure code, human-readable primary diagnostic, process exit code, termination kind, and diagnostic source. Raw `stdout.log` and `stderr.log` remain raw logs and are not containers for synthetic Factory diagnostics. Normalized diagnostics must not contain full raw logs, API keys, credentials, or authentication payloads.

Live handling and persisted-attempt recovery use the same classifier and normalized diagnostic model. If Factory restarts after process telemetry was persisted but before `failure-diagnostic.json`, recovery reconstructs the same classification from persisted telemetry and bounded raw logs. Recovery and event recording are idempotent: the same failed invocation must not decrement budgets twice, duplicate external-blocker events, or create a second semantic operation.

## Continuation contract

An external blocker is `Blocked` with a resumable `SemanticInvocation` continuation. It preserves the original `Operation` and `OperationInput`; `WorkItemId` is preserved for execution and is null for planning. The user-facing resume instruction is to resolve the external Agent Backend condition and use `factory_continue`, not to replace the Factory run.
