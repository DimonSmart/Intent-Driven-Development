# IDD-0001.spec-factory-orchestration

## Intent

IDD Factory provides lightweight temporary orchestration for implementation
requests that benefit from decomposition and context isolation.

Factory is defined by this semantic loop:

```text
complete logical request
-> Factory Preflight
   -> Product Intent analysis
   -> explicit Engineering concern detection
   -> idd-engineering-change when required
   -> existing Product Intent workflows when required
   -> durable coverage validation
-> fresh initial planner (Factory inactive)
   -> Question: exact answer -> authorized owners -> fresh planner
   -> Done: final verification, complete without active state
   -> Tasks: validate first batch -> create active Factory state LAST
-> current batch
-> fresh sequential worker per task
-> fresh planner
-> Question | Done
```

Factory is not a deterministic workflow runtime. IDD-0006 owns the architectural rationale; IDD-0012 owns recovery, provenance and refinement review; IDD-0013 owns model policy. IDD-0008 owns Engineering management.

## Two-level context rotation

`idd-factory-run` is the thin Supervisor and does not run Preflight,
Planner, Workers, verification, recovery, or edit temporary/durable project
state. It launches **one fresh generic Factory Root per batch**, waits for
a trusted normal native terminal result and automatically continues only
on strict CONTINUE/BATCH_LIMIT after Root attests its verified checkpoint.
Aborted/untrusted terminals never count, and forced OS cancellation is host
responsibility. Expiration of a native wait interval is **not** a child terminal.
The internal `idd-internal-factory-root` owns orchestration and mandatory
normative references, including the exact materialized
request, immutable Git baseline, authorized Engineering and Product owner
order, Planner `# Task/# Question/# Done`, ExecutionProfile, checkpoint,
Intent Refinement Review and final verification.

Default `max_workers_per_batch=8` is a positive invocation-only
**target**, not a hard upper bound. Each fresh Root starts with zero
confirmed Workers. It increments its own transient `completed_workers`
only after a Worker has a trusted successful native terminal and the
existing `provenance.md`, `completed.md`
and remaining `plan.md` checkpoint is verified by Root.

Every freshly generated Planner result contains **at most four**
`# Task` sections; five or more is a protocol blocker before saving
the plan or starting any Worker. Do not truncate it, automatically retry
or introduce a configuration setting. This does not invalidate a
previously saved plan with more than four Tasks.

Root executes every remaining Task from the current Planner plan even
when the counter reaches the target mid-plan. Only after the WHOLE
plan is finished with trusted normal Worker terminals, all pending
checkpoints closed, and the saved state reconciled can it return
`CONTINUE / BATCH_LIMIT` with the ACTUAL Root-local number of Workers,
which may exceed the target. An empty plan alone is not evidence.
If the target is still unmet, a fresh Planner runs normally; if reached
at the plan boundary, the next Root begins from a fresh Planner and
may finish with `# Done`. Faults, stale Tasks, untrusted checkpoints,
resource exhaustion or uncertain native completion follow existing
BLOCKED/NEEDS_INPUT and recovery rules, not a normal rotation.
Supervisor checks only the correlated successful native Root terminal,
strict terminal fields, Worker count versus the rotation target and the
active `current/request.md` marker. Root alone checks the plan boundary,
Worker outcomes and saved provenance/completed/remaining-plan consistency;
Supervisor does not duplicate these checks or interpret Product Intent.
Neither Root nor Supervisor introduces new persistent Factory state.

Root's strict plain-text terminal fields are exactly one each:
`Status`, `CompletedWorkers` and `Reason`, plus exact
`QuestionFile` when applicable. No separate Supervisor state or batch
checkpoint files, no custom workflow/process runtime, and no changes to
`.idd/execution.yaml` are permitted. Native task names must uniquely correlate each Root batch and each nested Planner/Worker attempt. Historic flat names remain report-compatible but are not emitted by new runs. No parent/child history inheritance. The Supervisor's context increases by short batch
results, not full Worker/Planner transcripts; capacity is finite.


## Native child-agent capability and internal Skills

A supported adapter must provide native generic child contexts with explicitly
disabled transcript inheritance, shared repository and installed Skill file
access, bounded assignment transport, terminal result retrieval,
blocking/event-driven waiting and normal child lifecycle operations.
Exceptional interruption and OS process cleanup belong to the host; Factory
does not require a forced-cancellation proof before normal execution.
Supervisor and Root use long native blocking waits for their respective children, or truly event-driven waiting when available. Platform-specific argument names and wait interval defaults belong to the canonical execution instructions.
Native wait intervals are **not execution deadlines or automatic kill
limits**. A nonterminal native wait timeout must preserve the live child and
re-arm a long native wait on the SAME child, without spawning a replacement
or performing short progress/status polling. Only a real host failure,
explicit stop or unresolvable child status may block further orchestration;
timeout by itself must not trigger native interruption. When an explicit execution mapping is active, native
per-child model/effort settings must be honored exactly; inherit adds no
Factory-specific overrides. Planner is semantically read-only and uses host
read-only permissions when available. A separate child sandbox is optional.

The optional Factory plugin exposes two public Skills and three internal Skills; the core Intent plugin remains a separate dependency:

```text
idd-factory-run                    public Factory Supervisor command
idd-factory-configure              public model-selection command
idd-internal-factory-root          internal Skill; complete Factory Root protocol
idd-internal-factory-planner       internal Skill; Planner protocol
idd-internal-factory-worker        internal Skill; Worker protocol
```

The three internal Skills belong to `idd-factory` only and are packaged from the corresponding canonical Root, Planner and Worker sources for supported hosts.
No separate Factory-specific custom-agent types, native role registry or
registration helper are required. The host creates ordinary native child agents;
the child reads its complete installed internal Skill and required references
before any project work, validates a phase-appropriate bounded assignment and
returns `BLOCKED` without work when mandatory context is missing.

Before durable preflight, Root validates its installed Skill, both child Skill paths, required references and available native capabilities. The internal paths are resolved from the exact installed
`idd-factory-run` package, never from a source checkout, global name search,
plugin cache guess or project cwd. Root does not read or transmit Planner/Worker protocol bodies.
Each spawn carries the actual installed absolute Skill path, an instruction to
load it fully first, the repository root, fresh-context requirement and only
bounded request/task, exact Q/A, baseline/provenance and selected Intent/
Engineering IDs. The host must explicitly disable transcript inheritance and correlate native child results. A host-specific custom agent type is not required. A native task name alone does not prove loading, model settings or completion.

Both roles receive fresh contexts with no Root/previous-child transcript.
The Planner performs semantic read-only decisions; each Worker executes exactly
one self-contained Task. Optional Engineering malformed structure blocks
implementation; an absent Engineering layer is normal. Root mechanically
propagates Always Rules while Planner selects Conditional Rules. Internal names
are not access control: a direct invocation without full valid Factory context
returns `BLOCKED`. Native hosts still own lifecycle, waiting and interruption;
no custom process runtime or model-driven polling is introduced.

## Phase ownership and public entry modes

The Supervisor chooses the public entry mode, checks native host and installed
Root capabilities, dispatches one Root at a time, waits for trusted normal
terminal results, validates the compact CONTINUE result and checks the active
request marker before rotation. It does not inspect nested Worker execution
or revalidate Root's plan checkpoints. Semantic Preflight, durable mutation,
recovery, Planner/Worker execution and final verification belong to Root.

| Operation | Accountable owner |
| --- | --- |
| Select New / Continue / Answer / Restart / Cancel and dispatch a native Root | Supervisor (transport only) |
| Validate request identity, scope, saved Q/A, Git baseline and Preflight | Root |
| Authorize and checkpoint durable owner handoffs; validate coverage | Root |
| Modify Product Intent decisions / Engineering Rules | Existing Intent owner / `idd-engineering-change`, respectively |
| Produce Tasks, Questions, Done and select related Conditional Rules | Planner |
| Execute one assigned Task, local checks and eligible monotonic Intent refinements | Worker |
| Persist preparation, active markers, Worker checkpoints and recovery evidence | Root |
| Verify completed-plan evidence, Worker terminals and checkpoint before returning CONTINUE | Root |
| Validate trusted native Root terminal, CONTINUE fields/count and active request marker before rotation | Supervisor |
| Run final project verification, Intent Refinement Review and cleanup | Root |
| Reject abnormal or uncertain native completion before another Root | Supervisor; host owns exceptional OS process cleanup |

`New` begins independent Preflight only without an active run or recoverable
preparation. If one exists, ask for an explicit choice: Continue existing work
(possibly to the next full-plan checkpoint), Restart or Cancel. Never silently
run unrelated work or advance the old request on behalf of a new one.
`Continue` resumes saved active state
or preparation without repeating new-run Preflight. `Answer` is a continuation
bound to the exact saved question and original request; a request-level blocker
that left no preparation cannot be reconstructed from a standalone answer.
`Restart` explicitly requests replacement: active runs follow replacement
Preflight and the Engineering guard. For interrupted preparation, Root first
reconciles saved request, baseline, provenance, pending owner actions and actual
repository changes; it may discard temporary preparation only when the outcome
is unambiguous and the replacement is explicitly authorized. Otherwise it
preserves evidence and requests a concrete user decision with NEEDS_INPUT.
`Cancel` asks Root to clean up temporary state only after safe writer/owner
absence of known ongoing Factory execution; it never reverts durable
decisions or repository work. Successful
Cancel returns `Status: COMPLETED` with `Reason: CANCELLED`, not `DONE`. None of these modes permits
Supervisor to change Product Intent or Engineering Rules.

## Factory entry preflight

For a new run, the public `idd-factory-run` Supervisor passes the complete
self-contained logical request to a fresh internal Factory Root. Root owns
the materialization, persistence and semantic Preflight of that request, which
remains authoritative throughout implementation. Route summaries, generated
plans, Engineering summaries and Intent diffs do not replace the request.

Root resolves requested scope, performs non-mutating Product Intent analysis
and separately decides only whether explicit durable Engineering management
is required. Factory does not duplicate Engineering semantic ownership,
equivalence, add/modify/remove/no-op, INDEX or allocator logic.

When explicit durable Engineering decisions are present, Root passes the
complete logical request to normal `idd-engineering-change` before active
Factory state exists:

```text
Root: materialize request -> analyze Product Intent and Engineering dispositions
-> reject request-level blockers before any durable write
-> new-run managed IDD cleanliness and original Git HEAD checks
-> persist preparation/request.md + baseline.md + provenance.md BEFORE owner mutations
-> checkpoint and invoke Engineering owner when required
-> checkpoint and invoke Product Intent owner when required
-> validate durable coverage and record approved boundary
-> fresh initial Planner while Factory is inactive
-> Question: save exact question; on answer, record exact Q/A, renew owners/coverage and replan
-> Task: validate batch -> prepare current/plan.md -> create current/request.md LAST
-> Done: configured final verification, without active state
```

`idd-engineering-change => success | no-op` allows preflight to continue.
`ambiguous | blocked` stops before active Factory state. Product Intent
mutation occurs only through the existing Intent workflows.

This order deliberately discovers authoritative Engineering ownership ambiguity
before Product Intent is written. It is not a transaction and does not add
rollback machinery.

`intent-preserving` forbids independent changes to approved Product decisions
and `.idd/engineering/*`, but Factory Worker alone may add verified monotonic
refinements to existing Intent owners unless the user forbids it. `intent-only` may perform required durable preparation
but does not start Factory implementation. Absence of `.idd/engineering/` is
valid and does not trigger bootstrap merely because Factory was invoked.

The full base request is persisted in `.idd/factory/preparation/request.md`
before the first Planner. `.idd/factory/current/request.md` remains the sole
active-run marker, written only AFTER the first valid executable plan has been
prepared. Initial Planner questions are allowed before activation and Workers
are not. Earlier durable preparation is renewed when a precise Planner answer
introduces a new authorized durable decision.

The existing Engineering active-run guard is never weakened. If an active
replacement request requires Engineering management, replacement is blocked
before durable writes; the user must complete/cancel the current run and then
start the complete replacement as a new run. No bypass, automatic
cancel/restart, temporary archive trick, or suspended lifecycle is part of the
contract.

## Autonomous technical decisions

Factory preserves mandatory Product Intent, current Engineering Rules and
scope while autonomously choosing implementation-local algorithms, libraries,
architecture and new-app configuration values. Neither longevity nor
architectural significance nor absence of an explicit "choose yourself"
phrase makes the choice a missing Engineering decision. A local choice
is not a new mandatory rule for future tasks; optional rationale does not
change its ownership. Missing `.idd/engineering/` is valid.

User delegation remains bounded; it never authorizes payments, account or
external identity registration, trust/signing policy, changes to published
identity or conflicting product behavior. Truly missing product/policy
decisions and incompatible constraints still block or require a concrete
question. Request-level blockers stop before durable writes and
`preparation/`; initial Planner `# Question` is after successful
preflight. `intent-preserving` prohibits changing preflight and allows only
bounded Factory Worker refinements;
active `current/request.md` continues to block Engineering mutations.

Planner selects Conditional Rules for realistic Worker-delegated choices
before Worker spawn or constrains/researches the approach first. Worker
honors assigned Always/Conditional Rules and reports missing coverage as
a blocker rather than editing its packet. Technical research requires
evidence and a fresh Planner before dependent Tasks.

## Planner protocol

The Planner returns exactly one normal outcome:

- one or more `# Task` sections, each followed by exactly one required
  `# ExecutionProfile` and optional `# TaskRelatedIntent` and
  `# TaskRelatedEngineering`;
- one `# Question`;
- exactly `# Done`.

A failed prerequisite instead returns the diagnostic `BLOCKED`, followed by exactly one nonempty single-line `Reason:`. This is not a normal outcome and must not be mixed with Tasks, Question or Done. Blank, incomplete, mixed or otherwise malformed output blocks orchestration.

Planning is incremental. The planner contracts only implementation/research
work knowable now. It never creates tasks that mutate Product Intent or
Engineering Rules or invoke their durable management workflows. A later task
whose contract depends on unfinished work is deferred until a fresh planner can
observe the changed repository.

A batch may contain multiple already-contractable tasks. Workers execute them
sequentially.

Each newly generated task must declare exactly one execution profile: `economy`,
`standard`, or `strong`. Missing, empty, repeated, or unknown metadata is malformed
new output. When reading existing pending tasks in `plan.md`, a missing section
means `standard` without migration or restart. Explicit empty, repeated, or unknown
profiles remain invalid. The planner classifies required execution capability
only; it never reads model policy,
emits concrete model IDs, or chooses vendor-specific reasoning settings.

## Task-related durable knowledge

Task-related references are not another durable-knowledge layer: they point to existing current documents without copying or deriving another source of truth. For product intent, semantic relevance belongs to the planner. It selects stable
`IDD-NNNN` IDs in `TaskRelatedIntent`.

For optional Engineering Guardrails, the planner selects only semantically
relevant Conditional `ENG-NNNN` IDs in `TaskRelatedEngineering`. It never
lists Always Engineering Rules.

Mechanical resolution belongs to the worker/host:

```text
IDD-NNNN -> exactly one current .idd/intent/IDD-NNNN.*.md
ENG-NNNN -> exactly one current .idd/engineering/ENG-NNNN.rule-*.md
```

Before each worker execution, the orchestrator deterministically enumerates the
current Engineering INDEX entries with `Applicability = Always` and supplies
them separately as `AlwaysEngineering`. The set is recomputed at execution
time and is not planner output.

The root orchestrator does not load selected documents merely to forward their
contents. The worker resolves and reads the current documents itself. The internal Skill
already has host-loaded instructions and, when Engineering exists, the complete
Guardrails contract separately from the task assignment. No worker inherits
parent skill references or a previous worker transcript.

Conditional Engineering applicability is semantic and belongs to the planner.
Always applicability, stable-ID resolution, and structural validation are
mechanical protocol operations. Do not use filename, keyword, path, extension,
project-type, embedding, or similarity heuristics to select Conditional rules.

There is no `RelevantCompletedWork` protocol. New task contracts are
self-contained. If a semantic fact from earlier work cannot be recovered from
repository reality, the next planner includes only the required fact in the new
task contract.

The persisted Markdown state, original Git baseline, provenance, recovery and at-least-once contract are owned by IDD-0012.

## User questions

An initial Planner Question is saved in preparation and stops orchestration.
The original request and every exact question/answer survive across sessions.
The answer is classified against the full context and requested scope. A local
implementation decision changes no durable rule; an authorized Engineering
decision uses `idd-engineering-change`, and an authorized Product change uses
the usual Intent workflow. When both apply, Engineering precedes Intent.
Blocked/ambiguous or scope-conflicting answers retain preparation without
activation. On authorized success/no-op, revalidate coverage and spawn a NEW
isolated Planner; never resume the former child.

After activation the existing Engineering guard remains in force: a later new
durable Engineering decision cannot mutate Rules inside the active run. Keep
Factory paused and require completion/cancellation followed by a new complete
request. Ordinary active-run questions retain their existing behavior.

## Verification and completion

Workers run reasonable task-local checks.

After Planner `# Done`, including before the first Worker, Factory runs the
configured `final` project verification. If the policy is absent, it must
discover and run the applicable repository/platform fallback; it may not
skip a discoverable check merely because the YAML is absent. If no
applicable final check can be discovered after successful discovery,
report that explicitly. Completion then requires conclusive evidence
for required task-local checks (or a genuine no-work `# Done`), without
claiming that a project-level check ran. An invalid configured policy,
incomplete discovery, or an assigned/discovered check that is unavailable,
refused, failed or unverified blocks approval.

Pre-activation success clears preparation without creating active state.
Failure is persisted as a bounded diagnostic
in the corresponding preparation or active location and supplied to a fresh
Planner. A repeated unchanged failure, missing confirmation or `Not verified`
cannot be silently declared success. Only valid correction Tasks activate a
previously inactive run.

Factory does not own a verification engine, attempt lifecycle, semantic retry
budget, correction workflow, or final semantic reviewer.

Completed temporary state may be removed or retained as diagnostic evidence under the recovery contract in IDD-0012.

## Intent Refinement Review

Root completes the refinement review defined in IDD-0012 before normal finalization.

## Design principle

Use semantic agents for semantic decisions and simple mechanics for mechanical
work. Do not solve Conditional Engineering relevance in code, and do not spend
model context on mechanical persistence, structural validation, stable-ID
resolution, or Always-rule enumeration.

Any proposed Factory feature that requires a new lifecycle state, transition
type, retry class, or exact recovery protocol requires separate architectural
justification.
