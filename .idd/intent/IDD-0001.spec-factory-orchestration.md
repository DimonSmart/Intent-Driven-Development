# IDD-0001.spec-factory-orchestration

## Intent

IDD Factory provides lightweight temporary orchestration for implementation
requests that benefit from decomposition and context isolation.

Factory is defined by this semantic loop:

```text
complete logical request
-> Factory Preflight
   -> Product Intent analysis
   -> explicit Engineering concern detection
   -> idd-engineering-change when required
   -> existing Product Intent workflows when required
   -> durable coverage validation
-> fresh initial planner (Factory inactive)
   -> Question: exact answer -> authorized owners -> fresh planner
   -> Done: final verification, complete without active state
   -> Tasks: validate first batch -> create active Factory state LAST
-> current batch
-> fresh sequential worker per task
-> fresh planner
-> Question | Done
```

Factory is not a deterministic workflow runtime.

## Native-agent capability

A supported adapter must provide:

- child-agent spawn;
- fresh semantic context with parent transcript inheritance disabled;
- shared current repository access;
- terminal waiting without model-driven polling;
- final child result retrieval;
- stop/close lifecycle control when needed.

Adapters may map these properties to platform-specific APIs. Canonical Factory
does not depend on those API names.

If a platform cannot provide the properties without a custom workflow/process
runtime, Factory may be unsupported for that platform. Do not preserve or
recreate a universal runtime for adapter parity.

## Semantic roles

Registered Factory skills are:

```text
idd-factory-run                   user command; orchestration and planner/worker lifecycle owner
idd-factory-configure             user command with automatic invocation; initial setup, exact edits, review, model refresh and authorized persistence
```

Internal Factory protocols:

```text
planner                       owned by idd-factory-run; fresh child context only
worker                        owned by idd-factory-run; fresh child context only
```

Neither protocol is a user-invokable skill. `idd-factory-run` explicitly
supplies the complete canonical planner or worker protocol to every fresh
native child. Worker instructions are packaged in
`references/factory-worker.md` under the run skill, and the complete canonical
Engineering Guardrails contract is supplied alongside them when the optional
Engineering layer exists. Each worker receives a separate one-task assignment.

No additional review, recovery, retry, finalization, or status role is part of
the core protocol.

Every planner and every worker runs in a fresh context. Children receive only
the explicit Factory packet plus repository access; they do not automatically
receive the root transcript or another worker transcript.

When `.idd/engineering/` exists, malformed or ambiguous Engineering structure
is a blocking implementation diagnostic. Absence of that optional layer is
normal.

## Factory entry preflight

For a new run, `idd-factory-run` materializes one complete self-contained
logical request and keeps it authoritative for the full preflight and later
implementation. Route summaries, generated plans, Engineering summaries, and
Intent diffs do not replace that request.

The entry workflow resolves requested scope, performs non-mutating Product Intent
analysis, and separately decides only whether explicit durable Engineering
management is required. Factory does not duplicate Engineering semantic
ownership, equivalence, add/modify/remove/no-op, INDEX, or allocator logic.

When explicit durable Engineering decisions are present, the entry workflow
passes the complete logical request to normal `idd-engineering-change` before
active Factory state exists:

```text
Product Intent analysis
-> Engineering management when required
-> Product Intent mutation through existing Intent workflows when required
-> durable coverage validation
-> persist preparation/request.md -> fresh initial planner
-> Question: persist exact Q/A -> authorized durable owners -> revalidate -> fresh planner
-> Task: validate batch -> prepare current/plan.md -> create current/request.md LAST
-> Done: configured final verification, without active state
```

`idd-engineering-change => success | no-op` allows preflight to continue.
`ambiguous | blocked` stops before active Factory state. Product Intent
mutation occurs only through the existing Intent workflows.

This order deliberately discovers authoritative Engineering ownership ambiguity
before Product Intent is written. It is not a transaction and does not add
rollback machinery.

`implementation-only` forbids mutation of both `.idd/intent/*` and
`.idd/engineering/*`. `intent-only` may perform required durable preparation
but does not start Factory implementation. Absence of `.idd/engineering/` is
valid and does not trigger bootstrap merely because Factory was invoked.

The full base request is persisted in `.idd/factory/preparation/request.md`
before the first Planner. `.idd/factory/current/request.md` remains the sole
active-run marker, written only AFTER the first valid executable plan has been
prepared. Initial Planner questions are allowed before activation and Workers
are not. Earlier durable preparation is renewed when a precise Planner answer
introduces a new authorized durable decision.

The existing Engineering active-run guard is never weakened. If an active
replacement request requires Engineering management, replacement is blocked
before durable writes; the user must complete/cancel the current run and then
start the complete replacement as a new run. No bypass, automatic
cancel/restart, temporary archive trick, or suspended lifecycle is part of the
contract.

## Autonomous technical decisions

Factory preserves mandatory Product Intent, current Engineering Rules and
scope while autonomously choosing implementation-local algorithms, libraries,
architecture and new-app configuration values. Neither longevity nor
architectural significance nor absence of an explicit "choose yourself"
phrase makes the choice a missing Engineering decision. A local choice
is not a new mandatory rule for future tasks; optional rationale does not
change its ownership. Missing `.idd/engineering/` is valid.

User delegation remains bounded; it never authorizes payments, account or
external identity registration, trust/signing policy, changes to published
identity or conflicting product behavior. Truly missing product/policy
decisions and incompatible constraints still block or require a concrete
question. Request-level blockers stop before durable writes and
`preparation/`; initial Planner `# Question` is after successful
preflight. `implementation-only` may not edit either durable layer;
active `current/request.md` continues to block Engineering mutations.

Planner selects Conditional Rules for realistic Worker-delegated choices
before Worker spawn or constrains/researches the approach first. Worker
honors assigned Always/Conditional Rules and reports missing coverage as
a blocker rather than editing its packet. Technical research requires
evidence and a fresh Planner before dependent Tasks.

## Planner protocol

The planner returns exactly one of:

- one or more `# Task` sections, each followed by exactly one required
  `# ExecutionProfile` and optional `# TaskRelatedIntent` and
  `# TaskRelatedEngineering`;
- one `# Question`;
- exactly `# Done`.

Blank output is malformed.

Planning is incremental. The planner contracts only implementation/research
work knowable now. It never creates tasks that mutate Product Intent or
Engineering Rules or invoke their durable management workflows. A later task
whose contract depends on unfinished work is deferred until a fresh planner can
observe the changed repository.

A batch may contain multiple already-contractable tasks. Workers execute them
sequentially.

Each newly generated task must declare exactly one execution profile: `economy`,
`standard`, or `strong`. Missing, empty, repeated, or unknown metadata is malformed
new output. When reading existing pending tasks in `plan.md`, a missing section
means `standard` without migration or restart. Explicit empty, repeated, or unknown
profiles remain invalid. The planner classifies required execution capability
only; it never reads model policy,
emits concrete model IDs, or chooses vendor-specific reasoning settings.

## Execution profiles and project model policy

Projects may optionally keep `.idd/execution.yaml` as persistent operational
policy. It is not Product Intent, an Engineering Rule, Factory temporary state,
or Factory runtime/workflow configuration. Absence means all profiles inherit
the normal host/session/default model behavior.

`idd-factory-configure` is the only entry point for initial model configuration,
exact replacements, changes to explicit reasoning settings, read-only review,
selection and lifecycle refresh, and authorized persistence. It can be invoked
directly by a person or automatically for a relevant request; activation alone
does not authorize a write. During initial setup the default-inherit versus
explicit-mapping strategy is chosen once. Review-only requests never create or
write policy. Exact unambiguous assignments need no duplicate confirmation;
automatically selected or ambiguously interpreted changes require explicit
approval, with an unchanged existing approval reused.

Partial mappings are valid: missing profiles/platform mappings inherit host
settings, including reasoning. A missing policy or global inherit does not
identify a concrete host model. The policy has exactly one strategy: global
`modelStrategy: inherit` or `executionProfiles` with only selected concrete
overrides. A per-platform return to inheritance deletes its mapping. The same
model may serve multiple profiles. Existing optional platform reasoning
settings, unmapped profiles, and other platforms are preserved unless the
user explicitly requests a change. Dynamic model-selection terms do not
become runtime model IDs.

Model selection may recommend upgrade or downgrade against current evidence;
a newer model is not sufficient reason to replace a working mapping. An
unverified model/account capability is reported as uncertain, not invented.
Known conflicts with preserved reasoning settings must be resolved explicitly.
Malformed existing policy blocks unauthorized replacement. The skill compares
the validated baseline with current policy immediately before save, does not
overwrite concurrent edits, and skips writes on no-op. Git owns history.

Immediately before every worker spawn, the root agent mechanically applies:

```text
planner profile
-> missing section in existing plan.md means standard
-> .idd/execution.yaml lookup
-> missing profile/platform mapping means inherit
-> inherit OR exact configured active-platform model/settings
-> native child-agent spawn
```

The root agent never reclassifies the task or substitutes a model. Malformed
explicit policy and host rejection of an explicit model/settings are blocking
diagnostics, not permission to fall back silently. The same canonical worker
protocol applies to every profile: profiles affect only native child-agent
settings, not worker instructions. The worker never selects its own model.

Policy changes affect the next worker spawn without requiring a new plan.
Already-created workers retain their model/settings. Model updates do not
change planner classification or temporary Factory state.

## Task-related durable knowledge

For product intent, semantic relevance belongs to the planner. It selects stable
`IDD-NNNN` IDs in `TaskRelatedIntent`.

For optional Engineering Guardrails, the planner selects only semantically
relevant Conditional `ENG-NNNN` IDs in `TaskRelatedEngineering`. It never
lists Always Engineering Rules.

Mechanical resolution belongs to the worker/host:

```text
IDD-NNNN -> exactly one current .idd/intent/IDD-NNNN.*.md
ENG-NNNN -> exactly one current .idd/engineering/ENG-NNNN.rule-*.md
```

Before each worker execution, the orchestrator deterministically enumerates the
current Engineering INDEX entries with `Applicability = Always` and supplies
them separately as `AlwaysEngineering`. The set is recomputed at execution
time and is not planner output.

The root orchestrator does not load selected documents merely to forward their
contents. The worker resolves and reads the current documents itself. The root
supplies the complete worker protocol and, when Engineering exists, the complete
Guardrails contract separately from the task assignment. No worker inherits
parent skill references or a previous worker transcript.

Conditional Engineering applicability is semantic and belongs to the planner.
Always applicability, stable-ID resolution, and structural validation are
mechanical protocol operations. Do not use filename, keyword, path, extension,
project-type, embedding, or similarity heuristics to select Conditional rules.

There is no `RelevantCompletedWork` protocol. New task contracts are
self-contained. If a semantic fact from earlier work cannot be recovered from
repository reality, the next planner includes only the required fact in the new
task contract.

## Temporary state

Factory persists only lightweight Markdown context, not an execution engine:

```text
.idd/factory/preparation/
    request.md               # complete original base request
    answers.md               # verbatim chronological Q/A, optional
    question.md              # pending exact question, optional
    verification-failure.md  # bounded final-check diagnostic, optional
.idd/factory/current/
    plan.md                  # validated remaining tasks before activation
    answers.md               # preserved Q/A, optional
    request.md               # sole active-run marker, written LAST
    completed.md             # later bounded worker summaries
    question.md              # later question, optional
    verification-failure.md  # later bounded failure, optional
```

An existing directory or an orphaned plan without the marker is not an active
Factory run. On continuation prefer an existing active marker; otherwise restore
valid preparation and its exact pending question without inheriting a transcript.
A new independent request cannot silently merge with that preparation. Explicit
cancellation removes preparation, not durable Product Intent or Engineering.
An interrupted activation must not trust partial inactive files without
verifying their provenance against saved preparation. A marker must not be
replaced to bypass Engineering guardrails.

The repository is authoritative implementation reality. `request.md` holds
the unchanged full base request; `answers.md` preserves exact Q/A separately;
`plan.md` contains only remaining tasks. Activation writes a valid plan and
answers BEFORE the marker and does not launch a Worker beforehand. Valid initial
Tasks are not re-planned merely because activation succeeded. No transaction,
locks, exactly-once promise, retry counter or runtime state schema is added.

## At-least-once execution

Factory deliberately provides at-least-once execution and semantic convergence,
not exactly-once execution.

If a worker is interrupted, its task remains first in `plan.md`. A later fresh
worker inspects current repository reality, preserves correct partial work, and
completes the task.

A failed native wait does not authorize a concurrent replacement writer. Stop or
close the child when possible, leave the task pending, and end the current
Factory invocation.

## User questions

An initial Planner Question is saved in preparation and stops orchestration.
The original request and every exact question/answer survive across sessions.
The answer is classified against the full context and requested scope. A local
implementation decision changes no durable rule; an authorized Engineering
decision uses `idd-engineering-change`, and an authorized Product change uses
the usual Intent workflow. When both apply, Engineering precedes Intent.
Blocked/ambiguous or scope-conflicting answers retain preparation without
activation. On authorized success/no-op, revalidate coverage and spawn a NEW
isolated Planner; never resume the former child.

After activation the existing Engineering guard remains in force: a later new
durable Engineering decision cannot mutate Rules inside the active run. Keep
Factory paused and require completion/cancellation followed by a new complete
request. Ordinary active-run questions retain their existing behavior.

## Verification and completion

Workers run reasonable task-local checks.

After Planner `# Done`, including before the first Worker, Factory invokes
existing configured `final` project verification when available, using the
existing absent-policy fallback. Pre-activation success clears preparation
without creating active state. Failure is persisted as a bounded diagnostic
in the corresponding preparation or active location and supplied to a fresh
Planner. A repeated unchanged failure, missing confirmation or `Not verified`
cannot be silently declared success. Only valid correction Tasks activate a
previously inactive run.

Factory does not own a verification engine, attempt lifecycle, semantic retry
budget, correction workflow, or final semantic reviewer.

Completed temporary state may be archived best-effort under
`.idd/factory/results/` or removed. The archive is diagnostic history, not
serialized runtime state.

## Legacy runs

Legacy `.idd/factory/current/state.json` is not migrated or interpreted by the
new Factory. Product changes are never rolled back automatically. An explicit
restart may reuse a valid legacy `request.md` as the replacement request and
archive old state for diagnostics.

## Design principle

Use semantic agents for semantic decisions and simple mechanics for mechanical
work. Do not solve Conditional Engineering relevance in code, and do not spend
model context on mechanical persistence, structural validation, stable-ID
resolution, or Always-rule enumeration.

Any proposed Factory feature that requires a new lifecycle state, transition
type, retry class, or exact recovery protocol requires separate architectural
justification.
