# Brainstorm Methods (optional reference)

This compact catalog is only for idd-intent-brainstorm when creative exploration benefits from a named technique. It is not a required checklist or execution engine. Every method produces **hypotheses**, not Product Intent.

## First Principles
Best when a conventional mechanism hides the actual user goal. Write the observable outcome and binding constraints; separate real limits from assumptions; rebuild candidate ways to achieve the goal. Example: "work with an archive" could mean browse contents, open externally or extract temporarily, not necessarily build an archive provider. Avoid when behavior is already unambiguously approved for implementation.

## Assumption Reversal
Best when a questionable assumption is universally accepted. Write the assumption, invert it, generate feasible product strategies under that inversion, then restore real constraints. Example: "every project needs editable permission rules" might become "a small fixed-role policy is sufficient". Avoid reversing non-negotiable legal or security requirements merely for novelty.

## Analogical Thinking
Best when an adjacent domain solved the same job. Identify the user job; find another workflow that addresses it; transfer the operating principle rather than copying a UI or unverified competitor claims. Example: saved playlists inspire saved file-selection sets. Avoid analogies that obscure important local limitations.

## Reverse Brainstorming
Best for discovering risks or unrecognized friction. Ask how to make the user's goal fail; list causes; reverse the most plausible into product changes or tests. Example: to make document search fail, hide errors and force repeated input; reverse into visibility and resilient navigation. Skip for a simple decision with well-understood trade-offs.

## Constraint Removal
Best when a limit is merely assumed. Explicitly identify confirmed versus assumed constraints, temporarily remove one assumed limit, invent a different strategy, then reapply confirmed restrictions. Example: if editing archives is not needed, a read-only view might avoid synchronization. Never waive safety or user approval.

## Opportunity Exploration
Best for open-ended product discovery. Trace actors' jobs and friction, identify adjacent unmet needs, and propose distinct interventions, including process changes and non-features. Example: a file manager could improve retrieval, grouping, batch operations, error visibility or onboarding. Avoid treating a confirmed code task as an invitation to invent features.

## No-New-Feature Alternative
Best when the user outcome may be achieved by changing defaults, documentation, process, UI guidance or existing controls. Compare the actual coverage of the need against net-new capabilities. Example: clear existing export feedback might remove the need for a workflow engine. It is not valid when the confirmed outcome genuinely requires new behavior.

## Transition to assessment
For each promising distinct principle: state its critical assumption, supporting evidence, disconfirming observation, cheap test, user value, costs, reversibility and risks. Keep fact versus hypothesis explicit. Treat an agent preference as provisional; only the user's approval permits an Intent Change handoff.
